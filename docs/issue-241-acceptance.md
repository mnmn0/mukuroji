## Required deployment approvals and concrete scope

### First-release and rollback baseline

The inspected default branch `501a788ae9495b30cb8f88d383436685939bf996` has no digest API or digest storage namespace. This is repository evidence, not verification of deployment history or cached clients. This work has not deployed the intermediate PR267–273 revisions and has not established any intermediate digest client/server as a supported production version. This document proposes the complete reviewed Web/server/worker stack as the first-release floor; that deployment and rollback policy is not user-approved. Parent/operator confirmation remains required. Before release, the operator must verify that no intermediate Web bundle, server, worker, or stored digest collection has been introduced independently. If that check finds an intermediate deployment, release is blocked pending an explicit coexistence/migration design.

Intermediate PR267–272 clients and servers are **not compatible** with custom selections: custom-only `views: []` fails their validation, and an older client can strip `savedFeeds` from a mixed selection during a write. Schema version 1 is a first-release schema here, not a promise of compatibility between draft revisions. Do not independently roll out PR273 over an intermediate digest release, serve cached intermediate bundles, or roll back writers to those revisions after custom preferences exist. A UI-only feature gate would not protect stored settings against an older server rewrite.

If the proposed floor is accepted, deploy the complete Web/API/worker release together before making custom settings available, and verify old intermediate bundles cannot remain active. The proposed operational rollback disables the worker/schedule/runtime control while retaining the compatible API for consent withdrawal and preserving metadata, receipts and checkpoints. Rolling code back below that floor requires taking digest writes offline first and a separately reviewed data/consent migration; it must not drop saved selections, insert a substitute enabled standard source, restore obsolete consent or reset receipts. No such migration or mixed-version support is implemented or claimed by this PR. These are proposed release prerequisites, not evidence of user approval or completed deployment/cache checks.

No item below has been deployed or enabled by this work. Approvals must identify the target AWS account, region, stage and reviewed infrastructure change; source-code approval is not deployment or live-notification approval.

Do not repurpose the existing notification scheduler without a separately reviewed binding change. Configure the existing `notification-schedule` runtime-control scope and a Lambda timeout with headroom for the 150-second shard-start budget, final 90-second shard and bounded SDK operations.
2. **Least-privilege policy approval:** existing Planning table `GetItem`/`PutItem`/`ConditionCheckItem` for delivery rows, `FENCE#.../META`, personal `UPDATE_FEED_DEFINITIONS#...` guards, and `SYSTEM#INBOX_DIGEST` checkpoint/failure rows; `Query` on this exact GSI. WorkspaceAccess, EnterpriseIdentity and TenantAdministration current authorization reads and transaction `ConditionCheckItem`; existing ProjectDirectory, Planning and Collaboration read operations used by the shared Feed resolver; current Cognito group reads scoped to the configured pool. Bind the existing application resource configuration, including Planning, Notifications, EnterpriseIdentity, membership/directory/collaboration/tenant resources and Cognito configuration. Independently saved user consent remains required. Disabling the schedule/worker flag or runtime control is the rollback path; retained receipts/checkpoints must not be deleted or reset merely to retry.
6. **Merge/Issue closure:** parent verifies each current head's applicable CI and Codex/CodeRabbit results, stack integration and acceptance. Main merge and Issue closure remain separately unauthorized here.
