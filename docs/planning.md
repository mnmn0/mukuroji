# Planning domain

Issue #27 の Planning domain は、短期の Cycle と中長期の Portfolio / Roadmap / Initiative / Goal、Project phase / Milestone / Release を一つの Workspace graph として扱います。Canonical Work Item 自体に計画フィールドを重複保存せず、Planning table の link row を正本にします。

## 永続化と並行更新

`PlanningTable` は `workspaceId` / `recordKey` を primary key とし、次の row を保存します。

- `META`（`workspaceId = FENCE#<workspaceId>`）: planning storage schema version、Workspace graph revision、Work Item による revision 前進を数える counter（`sourceRevisionCount`、`structureRevision`、`structureSourceRevisionCount`）
- `ENTITY#<id>`: planning entity
- `DEPENDENCY#<id>`: directed scheduling dependency
- `WORK_ITEM_DEPENDENCY#<id>`: Team-qualified Work Item 間の canonical schedule dependency
- `LINK#<teamId>#<workItemId>`: Work Item から Cycle / Milestone / Goal への link
- `UPDATE_TARGET#PROJECT#<teamId>#<projectId>` / `UPDATE_TARGET#INITIATIVE#<entityId>`: update owner、cadence、次回期限、latest version の bounded projection
- `UPDATE#<target>#<zero-padded-version>`: structured health update の append-only 正本
- `UPDATE_ID#<target>#<updateId>`: target 内で update ID の再利用を防ぐ immutable marker
- `UPDATE_COMMENT#<target>#<version>#...`: immutable update に対する append-only comment
- `UPDATE_COMMENT_ID#<target>#<version>#<commentId>`: update version 内で comment ID の再利用を防ぐ immutable marker
- `UPDATE_REACTION#<target>#<version>#...`: immutable update に対する member reaction
- `COLLECTION#<collectionId>`: Work Item を参照する整理用 Collection（[Collections](./collections.md)）。Planning graph の revision fence には含めません
- `COLLECTION_COUNT`: Workspace の Collection 数。作成・削除と同じ transaction で更新し、上限を強制します

Planning API snapshot は `schemaVersion: 2` を返し、Web は現在の schema version の snapshot だけを受け付けます。DynamoDB の storage schema version 1 は API contract から独立しています。Revision の正本は、graph row の `<workspaceId>` partition から分離した `FENCE#<workspaceId>` partition の `META` row だけです。

### Revision fence

Planning client は FENCE `META` だけを強整合 read し、row がなければ revision 0 として扱います。FENCE `META` の作成・更新は常に DynamoDB transaction 内の revision CAS（初回は `attribute_not_exists`、以降は `revision = expectedRevision`）で行います。Runtime の DynamoDB document client は、transaction 外の Put / Update / Delete による FENCE `META` への直接書き込みと、PartiQL / BatchWrite による書き込みを `PLANNING_REVISION_FENCE_BARRIER_REQUIRED` で fail-closed に拒否します。Canonical Work Item を書く worker には、`FENCE#*` partition の revision 属性を `TransactWriteItems` 内でだけ更新できる IAM 権限を付与します。

すべての mutation は snapshot の `expectedRevision` を必須とし、認可に使った snapshot と mutation の revision を一致させたうえで、`META` の revision CAS と対象 row を同じ DynamoDB transaction で更新します。Stale write は `409 PlanningRevisionConflict` で拒否し、階層、dependency、link の部分更新を残しません。Canonical Work Item projection は強整合 read で取得します。Workspace member の role / status 更新と Planning scope が参照する Team / Project の archive は、事前検査した `META` revision を directory mutation と同じ transaction で一つ進めます。並行する Planning create / move とは一方だけが成功し、競合側は最新 snapshot で再検査します。

Canonical Work Item の書き込みも同じ `META` の revision を進めます（roll-up の入力を1つの条件で守るため）。そのままでは Work Item が更新されるたびに Planning の操作が `409` になるため、Work Item の transaction は `revision` と一緒に `sourceRevisionCount` を1つ進め、Planning の commit は自分の revision を `structureRevision`、そのときの counter を `structureSourceRevisionCount` に書きます。`revision - structureRevision` と `sourceRevisionCount - structureSourceRevisionCount` が等しければ、最後の Planning commit 以降は Work Item だけが revision を進めています。counter を書かない writer（Workspace member や Team / Project の変更など）が進めた revision はこの差が合わないので、Planning の変更として扱います。

Work Item の状態に依存しない次の操作は、呼び出し元の `expectedRevision` が最後の Planning commit 以降で、そこから Work Item だけが revision を進めている場合も受け付けます: entity の作成・更新・複製・移動、entity 間の dependency の作成・削除、Work Item link の作成・置換、Cycle への Work Item の一括追加・削除。route は現在の snapshot で認可し、client は commit 直前に同じ条件を再検査します。読み取りから commit までの間に Work Item の書き込みが入って CAS が失敗した場合は、最大3回まで読み直して再試行します。Work Item link と Cycle への一括追加・削除は、認可に使った Work Item の revision を同じ transaction で検査します（link の作成・置換では、認可時の revision と Planning に渡す projection の revision が一致しなければ `409 PlanningWorkItemChanged`）。Work Item link の削除は Work Item の revision を検査しないため、完全一致のままです。Archive・restore・rollover・次の Cycle の作成・Work Item dependency・update の publish / cadence は Work Item の状態を読むか、`META` の revision を Work Item ごとの条件の代わりにしているため、従来どおり revision の完全一致を要求します。Graph の読み取りも、前後の `META` read の間に revision が進んだ場合は最大3回まで読み直します。

1 row は安全余裕を含む 300 KB、1 transaction は 100 item / 3 MB、API snapshot は4 MBを上限とします。Versioned update、comment、reaction は graph snapshot に展開せず、target-prefix の cursor API で取得します。Graph read は META の強整合 read を前後 barrier にし、mutable graph の5 prefixだけを強整合 Queryするため、増え続ける update history / annotation rowを物理的に走査しません。Entity description は UTF-8 で 20 KB までです。Project / Initiative report は entity に埋め込まず、versioned update を正本にします。上限超過は commit 前に `413` で拒否し、response だけ失敗して revision が進む状態を作りません。

### Live graph の容量

Live graph の row 数（`ENTITY#`、`DEPENDENCY#`、`WORK_ITEM_DEPENDENCY#`、`LINK#`、`UPDATE_TARGET#` の合計。`META` は含みません）は、1 Workspace あたり 20,000 row を容量とします（Issue #369 で 2,000 row から変更）。

- 容量は row 数と byte 数（各 row を保存する UTF-8 JSON の合計、24 MB）の両方で測ります。`UPDATE_TARGET#` row の `latestContextSnapshot` のように snapshot に出ない属性も byte 数に含めます
- 容量を超えて row 数または byte 数を **増やす** mutation だけを `413 PlanningCapacityExceeded` で拒否します。増やさない mutation（既存 entity の編集、link や dependency の解除、move、archive）は容量を超えていても受け付けるので、運用者は常に容量内へ戻せます
- Project / Initiative の update target は 2,000 件までです。Update Feed の projection と target ごとの activity 読み取りが同じ 2,000 件で上限を設けているため、2,001 件目を作る cadence 設定や publish を `413 PlanningCapacityExceeded` で拒否します
- 読み取りは容量より大きい 25,000 row / 32 MB を安全上限とし、これを超えた場合だけ `413 PlanningReadLimitExceeded` で fail-closed にします。書き込みが同じ数え方の容量で止まるため、通常の運用で読み取りが失敗することはありません
- Snapshot は `capacity: { level, liveRowCount, liveRowCapacity, warningRowCount, liveByteCount, liveByteCapacity, warningByteCount }` を返します。`level` は row 数か byte 数の一方が 80%（16,000 row / 19.2 MB）以上で `warning`、容量以上で `full` です。値は Workspace 全体の量で、entity ID や scope を含まないため、Planning を読めるすべての member に返します
- Planning 画面はヘッダーに使用量（`計画データの使用量: n / 20,000 行 · x / 24.0 MB`）を常に表示し、`warning` では注意、`full` では row を増やす変更が保存できないことを案内します
- 100 Project・link 済み Work Item 5,000 件（約 5,500 row、閲覧可能な Work Item 5,000 件）の Workspace で snapshot は約 3.1 MB に収まることを `planning.test.ts` で確認しています。閲覧可能な Work Item が 1 万件近い場合や、長い description を持つ entity が数千件ある場合は、row 数が容量内でも snapshot が 4 MB を超えて `413 PlanningSnapshotSizeLimitExceeded` になります。Snapshot に載せる Work Item を link 済みと依存の端点に絞る作業は Issue #459 で行います

DynamoDB client は、デコード済みの graph を META の `revision` と `updatedAt` が一致する間だけ Lambda の memory 上で再利用します（最大 8 Workspace、LRU）。`UPDATE_TARGET#` 以外の graph row は `META` の revision CAS と同じ transaction でしか書かれないため、強整合 read した `META` が一致すれば内容も一致します。`UPDATE_TARGET#` row は通知 schedule worker が `META` を進めずに due-index 属性を更新するので、cache hit 時も毎回強整合 Query で読み直し、Initiative entity との整合を再検証します。Tenant 削除は Planning row を `META` を進めずに消しますが、revocation の後に実行されるため、削除中の Workspace の Planning を読める principal はいません。Cache した graph は deep freeze し、読み取り側が共有 state を変更できないようにしています（in-memory client も同じく freeze した state を返し、テストで変更を検出します）。

#### 容量に近づいたときの運用手順

1. Planning 画面のヘッダー、または `GET /api/planning` の `capacity` で使用量を確認します
2. 使用量の大半は通常 Work Item link（Work Item ごとに 1 row）です。終了した Cycle、不要になった Milestone / Goal を archive すると、その entity と entity への link 参照・dependency が live graph から退避され、容量を消費しなくなります（下の「Archive と復元」）
3. Archive できない entity への link は、Project / Team manager が `DELETE /api/planning/work-item-links/:teamId/:workItemId` で解除します。Work Item 自体と Work Item の履歴は残ります
4. 不要な entity dependency と Work Item schedule dependency を解除します
5. 容量超過中も row を増やさない変更は保存できるため、上の操作は `full` の状態でも実行できます

Team / Project / Portfolio 単位の読み取りへの分割は、Issue #369 の後続の変更で行います。それまでは、critical path、roll-up、cross-Project dependency はこれまでどおり Workspace 全体の live graph から計算します。退避済みの entity と参照は計算に含めません。

#### Entity ID の採番

`POST /api/planning/entities` の `id` と `POST /api/planning/entities/:entityId/duplicate` の `targetId` は省略できます。省略すると server が `pe-` と 32 桁の 16 進数からなる ID を採番し、`Location` header（`/api/planning/entities/<ID>`）で返します。ID を指定した request はこれまでどおり受け付け、`Idempotency-Key` を見ません。

ID を省略する request には `Idempotency-Key` header（1〜256 文字、制御文字なし）が必要です。無いと `400 InvalidPlanningEntityIdempotencyKey` になります。採番は Work Item dependency と同じ Developer Platform の idempotency reservation を使い、呼び出し元ごとに key・method・path・body を結びつけます。

- 同じ key と同じ body の再送は、最初の request が作った entity の `Location` と現在の snapshot を `201` と `Idempotency-Replayed: true` で返し、entity を増やしません。再送の `expectedRevision` が古くても通ります
- 同じ key を別の body や別の path で使うと `409 PlanningEntityIdempotencyConflict`、最初の request が処理中なら `409 PlanningEntityIdempotencyInProgress` です
- ID は Workspace・呼び出し元・操作（作成 / 複製）・key の SHA-256 から決まります。commit 後に応答や受領記録の保存が失われても、同じ key の再送はその ID の entity（archive 済みを含む）を見つけて、作り直さずに同じく replay として返します。この確認は revision の確認より先に行うので、古い `expectedRevision` の再送でも通ります
- 権限の確認や validation など 4xx で失敗した request は reservation を解放するので、直した body を同じ key で送り直せます。5xx や通信の失敗など commit したか分からない失敗では reservation を残すので、同じ key の再送は最初の request と同じ body のときだけ通ります（reservation の lease の 2 分間は `409 PlanningEntityIdempotencyInProgress`）

Web の作成フォームと複製ボタンは ID を送らず、1 回の操作とその再試行で同じ `Idempotency-Key` を使います。通信失敗や 5xx など結果が分からない失敗の後は、snapshot を読み直していても、同じ内容の再送では最初の `expectedRevision` を送り続けます。body が変わると key も変わり、2 つ目の entity ができてしまうためです。`Location` は CORS の `Access-Control-Expose-Headers` で公開しています。

#### Archive と復元

`POST /api/planning/entities/:entityId/archive` は、entity を archive した revision を確定したあと、archive 済み entity を live graph から同じ Workspace partition の退避用 row へ移します。退避用 row の prefix（`ARCHIVE_ENTITY#`、`ARCHIVE_REF#`）は live graph の prefix と重ならないため、live の読み取りでは読まれず、容量にも数えません。退避用 row の key は複数の ID をつなぐため、DynamoDB の sort key の上限（1,024 byte）を超える部分は `#` と SHA-256 digest に置き換えます。ID そのものは row に保存します。

- 退避は entity ごとに、先に dependency と Work Item link の参照、最後に entity を移します。1 revision で書く item は 90 まで、書き込む row の合計は約 2 MB までなので（transaction の上限 3 MB に余裕を残すため）、link の多い Cycle や Goal は数 revision に分かれます（Goal と link 100 件なら archive を含めて 4 revision）。各 revision は live graph を検証してから META の revision CAS と同じ transaction で書くため、途中のどの revision でも live graph は整合しています
- Work Item link は Work Item ごとに 1 row で、Cycle・Milestone・Goal を同時に持てます。退避するのは archive した entity を指す参照だけです。ほかの参照が残る link は live graph に残り、残らない link は削除します。退避した参照は `ARCHIVE_REF#<entity>#LINK#<team>#<workItem>` に、参照を外す前の link とともに保存します
- 子 entity が live graph に残っている entity は退避しません（子は親を live graph で解決するため）。子を退避したあとに親を退避します
- Update target を持つ Initiative は archive しても live graph に残します。Update target と immutable update 履歴は通知 schedule と Update Feed が live graph から解決しており、update target は 2,000 件の上限で抑えられているためです。その親も live graph に残ります
- 1 request で進める退避は 40 revision までです。途中で止まった分（link が数千件ある場合や、同時編集による revision 競合が 3 回続いた場合など）は live graph で archive 済みのまま残ります。同じ entity の archive を再実行すると、archive の revision を作らずに続きを退避します（ほかの entity の archive でも続きが進みます）。Archive の response は退避後の snapshot を返します
- 退避中の entity と同じ ID の entity は作成・複製できません（`409 PlanningEntityExists`）。復元するか別の ID を使います

`GET /api/planning/archived-entities?limit=&cursor=` は退避済み entity を ID 順に返します（1 page 最大 50 件）。各 entity の Team / Project scope を manager 権限で確認し、呼び出し元が復元できるものだけを返します。そのため page の件数が `limit` より少なくても `nextCursor` が続くことがあります。Enterprise 認可では、一覧の route は Workspace 単位で認可されるため、各 entity の Team / Project（scope が無ければ Workspace）を resource として `planning.manage` を評価し直します。Team / Project 単位の付与だけを持つ利用者にも、復元できる entity が一覧に出ます。

`POST /api/planning/entities/:entityId/restore` は `{ expectedRevision }` を受け取り、退避済み entity を active に戻します。権限は archive と同じく entity の scope の manager で、親が live graph にある場合は親の member 権限も確認します。Enterprise 認可では、退避済み entity の Team / Project scope を認可対象の resource とします。Archive 中に owner が無効になった entity は、作成・複製と同じく `409 PlanningOwnerInactive` で拒否します。復元のすべての revision は、呼び出し元の Workspace membership（Enterprise 認可では control revision も）を同じ transaction で条件検証します。Service account には Workspace membership の row がないため、Enterprise の control revision だけを条件にします。復元の途中で membership や Enterprise の設定が変わると、その revision は失敗し、request は `409 PlanningAuthorizationChanged` になります。残りの参照は退避先に残ります。

Live graph に残っている archive 済み entity（update target を持つ Initiative とその親、退避の途中のもの）も同じ API で戻せます。この場合は live graph の中で `archivedAt` を外し、Initiative の update target も active に戻します（通知の due-index は cadence から作り直します）。

- 最初の revision は呼び出し元の `expectedRevision` で entity を戻します。親が live graph にないか archive 済みなら `409 PlanningRestoreParentUnavailable`、親の Team / Project scope が変わっていれば scope 不一致の 409 になり、entity は退避されたままです。先に親を戻すか、親を元の scope に戻します
- 続く revision で参照を最大 30 件ずつ戻します。Link の参照は Work Item の revision を同じ transaction で条件検証し、消費する退避用 row が残っていることも条件にします（同時に走った復元が同じ参照を二重に戻さないため）。各 revision は対象の entity が live graph で active なことを確かめ、復元の途中で別の操作が entity を archive し直した場合は参照を消費せずに止めます。Work Item の同じ欄が別の Cycle / Milestone を指している、link の Project が Work Item の現在の Project と違う、Cycle の capacity を超える、Goal が 100 件を超えるなど、戻すと整合しない参照は破棄します。破棄の判断も Work Item の revision を同じ transaction で条件検証し、途中で Work Item が変わった場合は参照を残して止めます。呼び出し元から見えない、または link を書けない（Work Item の Team と Project に member 権限がない）Work Item の参照と、削除・archive 済みの Work Item の参照は破棄せず退避先に残し、書ける人が復元を再実行すると戻ります
- Dependency は、相手の entity が live graph にあれば戻します（重複や循環になるもの、constraint を満たさないものは破棄）。Dependency の作成と同じく相手の entity の manager 権限も必要で（Enterprise 認可では相手の Team / Project を resource として評価します）、権限がなければ戻さずに退避先へ残し、両方を管理できる人が復元を再実行すると戻ります。参照を戻す各 revision では、戻す entity 自身の現在の scope でも manager 権限を確かめ直し、途中で管理できない scope へ移されていれば止めます。相手の退避先へ移す dependency は、ID と両端の entity を key に含め、同じ ID が別の edge に再利用されていても上書きしません。相手がまだ退避中なら相手の退避先に移し、相手を復元したときに戻します。相手が退避中かどうかは各 revision で live graph を読んだ後に確かめるので、復元中に相手が archive されても dependency は破棄されません
- 戻す参照は、各 revision で live graph を読んだ後に退避先から読み直します。退避用 row の変更はすべて revision を進めるので、確定した revision はその時点の row を消費します。同時に別の復元が参照を戻し、同じ ID で作り直されて再び退避された場合も、最初に読んだ古い内容ではなく現在の row を戻します
- 容量（20,000 row / 24 MB）や Planning snapshot の応答上限を超える分は戻さず退避先に残します。容量を空けてから同じ復元を再実行すると、active な entity に残っている参照の続きを戻します
- Response は `{ planning, restore }` です。`restore` は `restoredLinkCount`、`droppedLinkCount`、`restoredDependencyCount`、`retainedDependencyCount`、`droppedDependencyCount`、`pendingReferenceCount` を返します。`pendingReferenceCount` は復元の最後に退避先を読み直した件数です

Web の Planning 画面では、計画の作成フォームの下にある「アーカイブ済みの計画」を開くと一覧を読み込みます。Live graph に残っている archive 済み entity を先に、退避済み entity をその後に（「さらに読み込む」で次の page）並べ、どちらも manage できる scope のものだけを表示します。「復元」は上の restore API を呼び、戻した件数・戻せなかった件数・退避先に残った件数を表示します。退避先に残った参照があるときは「続きを戻す」で同じ entity の復元を再実行します。復元した entity は一覧から消えるため、参照が残っている結果は別の entity を復元しても残し、続きがなくなるまで表示します。復元の request が 404 以外で失敗したときは snapshot を読み直し、その entity が active に戻っていれば、最初の revision が commit 済みで参照が退避先に残っている可能性があるため、「確認できませんでした」という結果に「続きを戻す」を付けて残します（commit 後の最後の読み取りで `PlanningRevisionConflict`（409）になる場合や、途中で権限の変更を検出した `PlanningAuthorizationChanged`（409）もこれに当たります）。entity が archive されたままなら復元されていないので結果を残しません。snapshot も読み直せなかったときは、5xx・応答の形式違い・通信失敗・`PlanningAuthorizationChanged`・`PlanningRevisionConflict` を commit 済みの可能性ありとして扱います（commit 前に拒否された conflict でも、「続きを戻す」はもう一度復元するだけです）。続きが残っている結果は Workspace と member ごとにブラウザの localStorage にも entity ごとの key で保存し（同じ member の別タブが別の entity を同時に更新しても互いに消しません）、再読み込みや別の画面から戻ったときにも表示します。別の端末やブラウザから続きを戻すには restore API を直接呼びます。復元しようとした entity が live にも archive にもなくなっていた（404）ときは、その結果を消します。親が archive 済みのときと owner が active な member でないときは、その理由を表示します。

Team / Project の archive は、live graph に残る link と active な entity だけを確認します。退避済みの参照は確認しないため、archive 済み Cycle の link だけが残っていた Team / Project も archive できます。その Team / Project の entity を復元するには、先に Team / Project を戻す必要があります。

## 階層と roll-up

許可する基本階層は `Portfolio → Roadmap → Initiative → Goal/OKR` で、OKR は `Objective → Key Result` を表現できます。その下に `Phase → Milestone/Release` を配置します。Project 計画の実用性のため、Phase は Roadmap / Initiative の直下、Milestone / Release は Roadmap / Initiative / Goal の直下にも配置できます。Cycle と Portfolio は root です。Self reference、存在しないまたは archive 済みの親、循環は保存しません。親を archive する前に active な子を移動または archive する必要があります。Archive した entity の dependency と Work Item link の参照は、entity と一緒に退避用 row へ移り、復元すると戻ります（「Archive と復元」）。

Automatic progress は、関連 Work Item と子孫の現在状態から on-read で決定します。`completed` は 100、`started` は 50、`backlog` / `unstarted` は 0 とし、`canceled` は分母から除外します。同じ Work Item が複数経路から辿れる場合も、ancestor ごとに一度だけ数えます。Manual progress を指定した entity は 0〜100 の保存値を使います。Health は entity 自身の risk で補正し、`high` / `critical` は `off-track`、`medium` は少なくとも `at-risk`、`none` / `low` は報告された health を effective health とします。`rollupHealth` は自身と active な子孫の effective health のうち最も悪い値を返します。

## Cycle rollover

Cycle は date-only の baseline / forecast、cadence、Work Item 件数単位の整数 capacity、carry-over policy を持ちます。Link と rollover は capacity 超過を commit 前に拒否します。Rollover は source / target Cycle が同じ Team / Project scope と cadence で、target の baseline / forecast が source より後に始まることを確認し、source を `completed` にします。

- `move-incomplete`: `completed` / `canceled` 以外の Work Item link を target Cycle へ移動
- `keep-incomplete`: 未完了 link を source Cycle に保持

Response は再計算済み snapshot と `movedWorkItemIds` / `retainedWorkItemIds` / `remainingWorkItemCount` を返すため、同じ入力と revision から結果を再現できます。

1回の rollover で移動する link は49件までです。未完了が49件を超える場合、その呼び出しは49件だけを移動して source を完了せず、`remainingWorkItemCount` に残りの件数を返します。同じ呼び出しを繰り返すと続きを移動し、残りが0件になる呼び出しで source を `completed` にします。画面の rollover は残りが0件になるまで自動で繰り返します。移動した link には `carriedOverFromCycleId`（元の Cycle）と `carriedOverAt` を記録し、これが持ち越しの履歴になります。Cycle を手で変えるとこの記録は消えます。

`PLANNING_TABLE_NAME` を設定した環境では canonical Work Item の書き込みが Planning META の revision を進めるため、呼び出し元の `expectedRevision` の CAS が Work Item の変化を検出し、Work Item ごとの条件検証は行いません。設定しない local 環境では canonical Work Item revision を Planning META と同じ DynamoDB transaction で条件検証します。Transaction の100 item上限に合わせ、途中の呼び出しは移動する link だけを、source を完了する呼び出しは source に残る全 link を検証し、どちらも49件までです。削除済み・閲覧不能の Work Item が link された場合は rollover を fail-closed にし、Workspace owner / admin が既存の DELETE API で stale link を清掃してから再実行します。Work Item の Project が変わった link は snapshot / roll-up から除外し、新しい Project scope へ明示的に再 link するまで rollover を拒否します。

## Cycle の自動作成・自動持ち越し・一括追加

設計の判断は [ADR 0010](adr/0010-cycle-schedule-due-index.md) にあります。

Cycle は `automation: { createNext, rolloverAtEnd }` を持てます（Cycle 以外は持てません。両方 false または `null` の patch で解除します）。日付は date-only なので、期日の判定は UTC の日付で行います。

- `createNext`: 終了日（baseline と forecast の遅いほう）の3日前の 00:00 UTC から、次の Cycle を作ります
- `rolloverAtEnd`: 終了日の翌日 00:00 UTC から、次の Cycle へ rollover します。次の Cycle がまだなければ先に作ります

Automation は呼び出し元の権限なしで `/next` と rollover を実行するので、設定・変更・作成時の指定には Cycle の scope での manager 権限（Enterprise では `planning.manage`）が必要です（`PATCH /api/planning/entities/:entityId` と `POST /api/planning/entities` で `automation` を含むとき）。複製した Cycle は automation を引き継ぎません。`rolloverAtEnd` が有効で次の Cycle がある間は、どちらかの Cycle の日付・cadence・scope を、次の Cycle が前の Cycle の終了後に始まり同じ cadence と scope を持つ状態から外す変更を `409 PlanningCycleNextIncompatible` で拒否します（先に `rolloverAtEnd` を外すか、手で rollover します）。

次の Cycle は `POST /api/planning/cycles/:cycleId/next`（source の manager 権限）でも作れます。元の Cycle の終了日の翌日から cadence の1回分（週なら `count × 7` 日、月なら `count` か月）の baseline / forecast を持ち、Team / Project scope、owner、cadence、capacity、carry-over policy、automation を引き継ぎます。Title は末尾の数字を1つ進めます（`Sprint 12` → `Sprint 13`、数字がなければ ` 2` を付けます）。ID は元の Cycle ID から決まり、元の Cycle に `nextCycleId` を記録するので、同じ Cycle から次を2回作ることはできません（`409 PlanningCycleNextExists`）。

自動化は既存の scheduled-jobs Lambda の `cycle-schedule` job が1時間ごとに実行します（runtime control は automation と共有します）。自動化の期日が来ていない、または完了済みの Cycle を除き、Cycle の `ENTITY#` row は `UpdateScheduleDueIndex` に `planning-cycle-00..15` の shard と期日の sort key を持ちます（update target の shard とは名前が違うので、通知の schedule は読みません）。Job は期日を過ぎた row を Query し、Cycle ごとに「次の Cycle を作る」「rollover を1 batch 実行する」を、やることがなくなるまで繰り返します。Rollover に使う Work Item は link 先の canonical Work Item を強整合で読み、archive 済み・削除済みの Work Item があれば手動の rollover と同じく fail-closed にします。前の Cycle の rollover がまだ残っている Cycle は、その rollover が終わるまで自分の rollover（完了）を待つので、job が止まっていて両方の期日を過ぎていても、前の Cycle の未完了 Work Item は取り残されません。失敗した Cycle は期日のまま index に残り、ほかの Cycle の処理は続けますが、失敗、Cycle ごとの手順の上限（1回の実行で20手順）で終わらなかった Cycle、page 上限（shard ごとに100 page）での打ち切りがあれば job 全体を失敗にするので、dispatcher の再試行と DLQ alarm に乗ります。

`POST /api/planning/cycles/:cycleId/work-items` は `{ action: 'add' | 'remove', workItems: [{ teamId, workItemId }], expectedRevision }` で、49件までの Work Item を1回で Cycle に入れる、または外します。Cycle と、移動元の Cycle の member 権限と、各 Work Item の member 権限が必要です（Enterprise permission は他の `/api/planning/cycles*` と違い `planning.manage` ではなく `planning.write` です。`/next` と rollover は `planning.manage` のままです）。入れるときは既存の Milestone / Goal の link を保ち、外したときに他の参照がなければ link を削除します。Capacity を超える場合は全体を拒否します。

Cycle を archive できるのは、残っている link の canonical Work Item がすべて `completed` / `canceled` の場合だけです。未完了なら先に rollover または unlink が必要で、canonical Work Item が削除済み・閲覧不能なら fail-closed に拒否します。`PLANNING_TABLE_NAME` を設定した環境では、archive は Work Item ごとの revision を条件検証しません。Canonical Work Item の作成・更新・削除は同じ transaction で Planning META の revision を進めるので、呼び出し元の `expectedRevision` による META の CAS が、snapshot 以降に link 先の Work Item が変わった場合を検出します。このため link の数にかかわらず archive は 1 transaction に収まり、link の参照はその後の revision で小分けに退避します。`PLANNING_TABLE_NAME` を設定しない local 環境では Work Item の書き込みが META を進めないため、archive の transaction で link 先の Work Item ごとに revision を条件検証します（transaction の上限から、link が約 97 件を超える Cycle は archive できません）。

## Project / Initiative health update

### Update Feed read model (Issue #241, first slice)

`GET /api/planning/update-feed?view=recent&limit=50` returns a live, permission-aware aggregate of the latest Project / Initiative summaries. Supported views are `recent`, `for-me`, `at-risk` (including off-track), `missing`, `stale`, and `overdue`. Health remains independent from submission state. Matches contribute to one target entry, not duplicate entries. The fourth slice below defines the current explainable relevance and attention ranking. Recent excludes targets without a report; submission views include them with unknown health.

The reader uses the existing bounded Planning graph (live capacity 20,000 rows, snapshot 4 MB), without loading Work Items, history, comments, or reactions. No update body, canonical row, or feed copy is written. Each request revalidates active directory hierarchy, current target permissions, and the latest summary's captured scope, reusing request-local directory and ACL reads across targets. Archived and revoked targets are excluded. Moved-scope or unprovable legacy summaries are removed while their currently authorized targets retain submission state and owner relevance with unknown health. Infrastructure errors fail the request rather than returning a partial success. Responses whitelist public summary fields and retain target identity plus immutable version for existing history/detail APIs, which continue to authorize their own reads. Duplicate `view` or `limit` query parameters are rejected as ambiguous.

`limit` accepts 1–100 (default 50); `total` counts only authorized matches and `truncated` explicitly reports omitted matches. This remains a bounded top-N API rather than cursor pagination. Personal state, saved definitions, activity signals and manual digest previews are described below. Daily/weekly Inbox delivery code remains inactive pending the rollout work below; Issue #241 stays open.

### Update Feed screen and personal state (second slice)

The Workspace `/updates` screen keeps the six standard views in its URL and links authorized target titles to existing Planning history/evidence panes. Target titles come from the current authorized directory/Planning graph, with `locale` passed from the active UI and included in its cache key. Health, submission freshness, ranking reasons, and personal read status remain separate. Refreshes occur every 15 seconds and on focus; failed refreshes suppress cached rows. Permission denial has a dedicated non-retry state; guests can read authorized reports but cannot mutate personal state and see no mutation controls. Loading, empty, retry, conflict, and narrow-screen states are supported in Japanese and English. Inbox continues to show its existing event timeline.

`PUT /api/planning/update-feed/read-state` accepts `{target, version, read, expectedRevision}` and returns `{read, revision}`. Authentication precedes JSON parsing; the member and Workspace are resolved exclusively from the authenticated session. Only the currently readable latest immutable version may be changed; archived, revoked, moved-scope, and obsolete reports return unavailable. A Planning revision is captured before fresh authentication/directory checks and compared with the loaded graph; the commit checks that same revision, active Workspace membership/version for human callers, Enterprise CONTROL revision when configured, and personal state CAS in one transaction. Service accounts require the Enterprise control guard and omit the nonexistent human membership row. Conditional-only conflicts return 409; mixed/transient transaction failures return a stable retryable 503, while unknown/malformed persistence failures return a stable 502. Conflicts require a refresh before another explicit choice. This does not change canonical report content or Planning revision. Read-state writes do not create events or send notifications.

The existing Planning table stores compact `UPDATE_FEED_READ#<member hash>#<target/version hash>` rows in the owning Workspace partition, containing only schema version, boolean state, and state revision. They are excluded from bounded graph/history prefixes. There is no body copy or scan. At most 100 exact, strongly consistent `GetItem` reads run in groups of ten using existing permissions; missing rows are unread, corrupt rows/errors fail closed. State survives sessions and a new report version starts unread. Old state may remain stored after permission loss, but it is neither returned nor writable until that exact report is currently accessible. Existing Workspace export/deletion can identify the owning partition. No table, IAM, credential, or delivery configuration is changed.

### Saved custom feeds (third slice)

`GET /api/planning/update-feed/saved` loads the current member's personal collection. `PUT` on the same route replaces that collection with `{expectedRevision, feeds}`, supporting create, edit and delete without changing reports or read state. Each definition has a name, standard base view and independent Team, Team-qualified Project, Portfolio, Initiative, health and submission-state filters. Values within a dimension use OR; dimensions and the base view use AND. Empty dimensions impose no restriction. Collections allow at most 20 definitions, 80-character names, 20 values per dimension and 64 KB of serialized definitions. Unknown fields are discarded. Guests cannot write.

Definitions use one compact `UPDATE_FEED_DEFINITIONS#<member hash>` row in the existing Workspace partition and one strongly consistent exact read. A single transaction checks personal revision plus current member/version and Enterprise control guards. Missing authorization guards fail closed; conflicts return 409, known transient failures 503 and malformed persistence 502. Concurrent editing never silently overwrites another device: the screen retains the draft on conflict and requires reopening with fresh state. No graph/history scan, update body copy, new table or IAM change is introduced.

`GET /api/planning/update-feed?feedId=<id>` resolves only the caller's own definition, then reapplies current target and captured-scope authorization before filtering and before the top-N limit. An explicit incompatible base view returns 409; an unknown personal ID returns 404. Saved opaque conditions do not grant access. `GET /api/planning/update-feed/options?locale=en` derives current readable labels from the bounded graph and active directory, without returning report bodies. A Project belongs to a Portfolio filter when a currently readable, active Planning entity in its exact Project scope has that Portfolio as a readable active ancestor; an Initiative uses its own ancestry. No Work Item membership scan is used. Archived or inaccessible hierarchy paths contribute no Portfolio match. Duplicate target projections fail closed.

The editor opens current selector metadata on demand and supports narrow screens, keyboard focus restoration, loading, authorization denial and explicit deletion confirmation. Filter IDs whose targets become unavailable are retained as conditions, without re-exposing their old labels. Each dimension shows only an unavailable-condition count; editing another dimension preserves those conditions, while editing that dimension replaces them.

### Current relevance and compact activity (fourth slice)

Clients opt into expanded reasons with `relevance=2`; missing this parameter preserves the original owner (2) / author (1) reasons, scores and response shape, without signal reads. This keeps older cached Web clients working during deployment; the updated Web requests version 2 and also accepts legacy responses during server rollback. Unsupported or repeated versions return 400. Known watcher failures retain their stable error code and retryable 503 status at the Feed boundary.

The current `for-me` ranking extends the first slice: ownership contributes 8 points, explicit current Project membership 4, a current target watch 3, interaction within 30 days 2, and authorship 1. Workspace/admin visibility alone is not Project membership. Reasons are returned individually and explained in Japanese and English. Multiple matches produce one entry. Attention breaks relevance ties with comment activity (2) and reaction activity (1) within 7 days, then latest publication time and qualified target identity. Attention alone does not add an unrelated target to `for-me`. Other standard views remain chronological; health, submission and read state remain independent.

After current target authorization, the server reads only the caller's exact qualified watch keys, in strongly consistent batches of at most 100, bounded to 2,000 targets and three attempts for unprocessed keys. It never lists other members' watches. Membership uses current explicit Project grants and qualified legacy membership, not general Workspace permissions. Revoked or archived targets do not reach watch lookup. Activity is usable only for an authorized latest summary with matching immutable version and captured scope; future or expired timestamps contribute nothing.

Source comment/reaction additions atomically write one compact `UPDATE_ACTIVITY#<qualified target>` projection alongside the canonical annotation and existing authorization/idempotency conditions. A latest-version/archive condition and independent activity revision CAS prevent stale-version and concurrent annotation races; failed transactions leave neither annotation nor signal behind and return a retryable conflict. The projection stores only timestamps and the 32 most recently active distinct members, never annotation text, reaction values or update bodies. A new version resets its activity window. Reaction removal retains historical interaction, as explained in the UI. This bounded approximation and post-rollout-only collection are explicit: older annotation history is not scanned or backfilled.

The activity prefix is independently bounded to 2,000 rows / 4 MB and 20 pages, with strongly consistent reads, strict schema validation and duplicate rejection. Feed generation performs no writes to `UPDATE`, `UPDATE_TARGET`, annotations or activity. Existing table permissions suffice. Daily/weekly Inbox delivery has separate consent, storage and inactive worker composition described below; Issue #241 stays open.

### Manual digest preview (partial Issue #241)

`GET /api/planning/update-feed/digest` returns the authenticated member's settings and at most twenty bodyless generation receipts. `PUT` accepts `{ expectedRevision, preferences: { enabled, frequency, views, savedFeeds? } }`; frequency is `daily` or `weekly`, and the combined selection contains one through six unique standard views/member-owned saved definitions. Settings default to disabled. Enabling this preference enables manual previews only, never a live schedule. Client Workspace/member fields are ignored. Guests cannot change preferences or generate receipts.

`POST /api/planning/update-feed/digest/preview` manually generates the current UTC day or Monday-based UTC week. These are interval identities, not a publication-date filter: the preview contains the selected current unread reports, including older reports still unread. It reads at most 100 candidates per view from the existing bounded read model, deduplicates exact Team-qualified target/version identities, rechecks authorization and personal read state, and returns at most fifty entries with explicit `truncated`. Read entries in a source's top 100 may leave fewer than fifty results; no unbounded refill or history scan is attempted. Missing targets without published content are omitted.

The existing Planning table stores one member-scoped digest metadata row. CAS protects preference updates, a 60-second lease fences competing generators, and each interval permits at most three manual attempts. Expired or failed attempts can be retried by calling preview again. The server owns UTC interval and attempt decisions; the UI displays an exhaustion response until explicit Reload, then permits another explicit request without inferring the current server interval from the device clock. There is no automatic retry loop. Superseded workers cannot complete or release a newer claim. Completion and replay writes guard the Planning authorization revision plus current caller conditions. A changed preference or permission produces a conflict rather than returning a stale preview. Infrastructure failures propagate and leave either a bodyless failure receipt or an expiring lease if cleanup fails.

Completed receipt replay recomputes content under current permissions and read state; no historic summary, title, target identifier, error text, or notification body is retained. Receipt counts describe the original completion and can differ from a later freshly authorized preview. Generating a preview does not mark reports read or mutate canonical updates.

The Updates screen now exposes a keyboard-accessible Digest preview disclosure. It loads settings/history only when opened, supports daily/weekly and standard-view preferences with explicit save, and offers manual generation only after settings are saved. The preview-only label is always visible. Receipt statuses describe preview generation, never delivery. Permission failures remove settings and report content; conflicts offer metadata reload rather than automatic generation. Guests have read-only access.

Preview bodies stay in component-local memory, outside SWR and browser storage. They clear on edits, panel close, session/locale/view/saved-definition/Planning-revision changes, browser focus/visibility changes, or after fifteen seconds. Later previews always request fresh server authorization. A failed or changed custom-definition lookup also suppresses any supplied preview. Japanese and English copy, narrow-screen wrapping, keyboard disclosure/actions, conflict recovery and permission loss are covered by UI tests.

The public API and UI support manual preview and separate Inbox consent settings, each selecting one through six standard/custom sources combined. Optional `savedFeeds: { revision, ids }` pins this member's bounded personal collection (at most twenty definitions); digest metadata contains no copied name, filter scope or report. Both settings APIs validate the current owned collection and transactionally fence its revision. Generation loads it at most twice and builds one request-local authorized/enriched projection of at most 2,000 unique targets. Signals load once; custom filter scopes resolve lazily at most once per authorized target. Each source applies its predicates and ranking before selecting its top 100, for at most 600 selected candidates across six sources. This is a candidate limit, not the total projection-work limit. Deduplicated candidates receive independent final ACL and personal read-state checks; at most fifty unread entries return, without refill. Instrumented overlapping/disjoint six-source tests bound authorization to 2,000 initial plus at most 600 final checks, scope calls to 2,000, and signal loads to one. Completion/replay also fences the definition revision in the same transaction as the receipt/Inbox insertion. Changed or deleted definitions require explicit reselection; they never silently broaden a digest. Current ACL loss yields no unauthorized entries. Loading definitions show a pending state with no premature Clear action; unavailable selections expose a generic recovery message, not remembered IDs or labels. Consent withdrawal remains available while definitions load or fail. Live Inbox delivery remains inactive pending rollout. Issue #241 remains open.

The authorization port must resolve the current member, `planning.read`, tenant availability and Inbox channel preference, and return recipient-bound transactional guards. `DynamoDbInboxDigestStore` implements the atomic port with a single `TransactWriteCommand`: delivery metadata CAS, current caller guards, Planning revision fence (including absent revision-zero META), current Inbox preference version/absence and conditional notification creation. `UPDATE_FEED_INBOX_DIGEST#<member hash>` rows are separate from preview metadata. Completion verifies the current pending token, attempt and unexpired lease; ordinary preference/claim writes cannot manufacture completed receipts. Lost claim responses retain the lease for expiry; lost completion responses recover from the persisted receipt. Replays do not overwrite Inbox read/archive fields. Empty digests complete without an Inbox row. SDK-command-boundary tests evaluate every generated condition before applying either write; no real AWS operation was performed.

The Inbox row mapper uses the existing recipient/key/state format and is tested through `toNotificationItem`. It emits a generic link to `/updates`, with no report body, target ID, report title, summary, count or external delivery channel. Its generic notification title supports Japanese and English, selected by recipient composition; notification TTL is 365 days from its first claim time, retained across retries. Expired pending claims remain due at lease expiry even on the third attempt and are durably marked failed before another interval is selected. Opening the Feed uses current authorization and current content, not a stored digest snapshot.

The production worker connects scheduler-owned `deferDenied` maintenance for denied recipients: a strong read and revision/due-time CAS move only the sparse-index due time one hour forward. Consent, history and revision remain unchanged; no revoked caller guard is bypassed for a preference, claim or notification write. Once the GSI converges, the deferred rows no longer consume due-query pages until eligible again. Fresh authorization is checked then; denial is never treated as permanent revocation. Current authorized preference changes can supersede the backoff immediately. Lost acknowledgments safely reread the durable due time; concurrent settings or claims conflict rather than being overwritten. Page continuation and shard rotation remain required while the GSI is stale. SDK-model worker tests cover healthy later pages, repeated denial, durable restart and a lost maintenance acknowledgment without extending the original backoff.

`createInboxDigestScheduleHandler` accepts an explicit disabled-by-default configuration and a trusted clock. One call inspects at most 100 candidate recipients, deduplicates recipient/cadence/UTC-interval identities, checks current daily/Monday-week receipts, and returns failed recipients plus an opaque continuation. Its caller must persist retry candidates and continuation; the production checkpoint worker below supplies a separate durable orchestration path. The durable adapter defines (but does not provision) `InboxDigestDueIndex`: string partition `inboxDigestShard` across sixteen `inbox-digest#0..15` shards and numeric epoch-millisecond sort key `inboxDigestDueAt`, projecting the Planning primary keys. Disabled settings remove index attributes; claims schedule lease expiry, failed attempts wait sixty seconds, completed/exhausted intervals advance to the next UTC day/Monday. `listDue` inspects at most 100 index rows, returns `LastEvaluatedKey`, strongly rereads each metadata row, excludes stale/not-due/disabled candidates and rejects corrupt metadata. The GSI is a candidate hint, never an ACL source. Neither the candidate index nor an EventBridge target is deployed. No canonical update/history scan is added.

Candidate discovery binds both the original scheduling time and frequency before authorization or a claim can fail. The public bounded scheduler deduplicates by recipient and cadence-qualified UTC interval, not recipient alone or raw timestamps. Distinct intervals survive in either input order, while different timestamps in the same interval collapse. Its terminal outcomes retain recipient, original cadence/time, canonical interval and a safe reason code even when failure precedes metadata access. These identities are restricted recovery data, not log text. If current consent has a different frequency, the old logical attempt is acknowledged as cancelled without generating a receipt or notification; fresh discovery may then start the new cadence using its current time. Historical attempts lacking their original frequency are also cancelled rather than inferring a backdated cadence. The interval key, actual lease clock and first successful claim timestamp are separate concepts.

Continuation is a continuous discovery cursor, not a fixed-time run: each new page discovers recipients under its current clock and consent. Already identified retries carry their original time and frequency separately; freezing all later pages would incorrectly backdate newly discovered work. A tracked candidate encountering a live claim remains retryable even at exactly the same clock value after a lost claim acknowledgment. Receipt retention is ordered by logical date, with cadence as a tie breaker. Once twenty receipts fill the retained window, its oldest logical key is a durable lower boundary: earlier absent intervals are cancelled before claiming or evicting anything. Normal settings writes preserve history, and accepted generation/pruning never moves that boundary backward. This protects both empty and nonempty completed intervals after their individual receipts have been pruned.

The production worker uses `DynamoDbInboxDigestCheckpoints`, rather than the earlier transport-only scheduler. Sixteen shard rows in the Planning system partition `SYSTEM#INBOX_DIGEST` hold revision, 90-second exclusive lease/token, continuation and at most twenty pending recipient pairs. A discovered page and its continuation commit before delivery. Each acknowledgement uses the current revision/token and an unexpired lease; a crash resumes unacknowledged recipients, while the deterministic delivery receipt prevents duplicate Inbox rows. A separate `ROTATION` row reserves and advances the first shard with CAS before any work, so daily/hourly cadence, restarts and slow prefixes cannot pin the start. Reservation contention is bounded to three attempts; unknown state fails closed. An invocation visits at most sixteen shards and stops starting shards or recipients with fewer than five seconds of its 150-second admission budget or shard lease remaining. Configure the eventual Lambda timeout with headroom for an already-started SDK operation.

The dedicated composition initializes only current Cognito, Workspace membership, Enterprise read-only policy, directory, Planning/read-state, saved definitions, Collaboration, tenant state and Inbox/checkpoint adapters. Unrelated application ports reject use rather than silently supplying fake authorization. Infrastructure configuration is unchanged.

Known `UpdateFeedDigestConflict` outcomes wait for fresh authorization/settings evaluation, at most once per invocation with sixty-second backoff. They are counted as `deferred` without consuming infrastructure-failure attempts or quarantining a legitimate concurrent update. After three page-local deferrals, the checkpoint transaction moves the logical work into a bodyless `DEFERRED#<recipient hash>` record and releases its page slot. This lets a full twenty-recipient conflict page advance its cursor. Strongly rechecked GSI rediscovery restores the original `scheduledAt` and infrastructure attempt count; successful, disabled, denied or terminal acknowledgment removes the deferred record in the checkpoint transaction. Deferred records have no TTL that could silently discard unfinished intervals. Operators inspect them under existing restricted access if the source recipient no longer becomes due. Not every conflict lasts indefinitely: post-claim conflicts also consume the separate bounded receipt attempts.

Each pending and deferred item durably records its trusted original scheduling time and discovery frequency before delivery. Retries across UTC midnight or Monday keep that logical interval while current consent has the same frequency; a changed cadence cancels the old attempt, and later fresh discovery binds new work. Legacy items without an original cadence are cancelled instead of inferring historical consent. Leases, backoff and authorization use the current clock. The receipt's `startedAt` is the actual first successful claim time, retained across later claims; notification ordering and 365-day retention use that time, not discovery time. Only an exhausted failed third-attempt receipt with unchanged cadence may roll into a later interval; completed receipt replay cannot generate a new interval. A live lease encountered by older logical work defers acknowledgment. Cancellation removes parked work atomically with the checkpoint acknowledgment.

The delivery failure classifier inventories deterministic read invariants separately from SDK availability: `UpdateFeedTargetLimitExceeded`, `UpdateFeedReadStateLimit`, `UpdateFeedReadStateInvalid`, `UpdateFeedViewInvalid`, `UpdateFeedLimitInvalid` and `UpdateFeedDigestInvalid` are invalid-input terminal outcomes; duplicate targets, invalid signals, corrupt digest/read-state/saved-feed rows and corrupt tenant state require operator inspection. Validated batches normally cannot reach the read-state/view/query limits. SDK reads of saved definitions keep unknown transport errors as `SavedUpdateFeedsStorageFailure`; only persisted parsing failures become `SavedUpdateFeedsCorruptState`. Unknown digest/read-state/tenant transport failures remain bounded retries, not success or terminal corruption. Recipient mismatch and typed permanent digest storage errors are terminal; authorization denial and disabled preferences are normal acknowledgments. Write-only saved-feed/read-state validation/conflict errors are outside the digest read path. Untyped port failures remain retryable rather than being classified by message or HTTP status alone.

Transient/unknown failures remain pending with a sixty-second backoff. After three such worker failures, removing the pending recipient and writing a bodyless failure record happen atomically. Proven persisted corruption and known permanent SDK/configuration failures use that atomic quarantine path on the first attempt; an unknown SDK/network failure is not classified as corruption. Production candidate reads skip that recipient until the next UTC day. If preclaim failures exhausted the worker budget before the receipt's own budget, fresh discovery then selects the oldest unfinished, unexhausted receipt under current cadence and preserves that interval through checkpoint admission. A cross-midnight/Monday failure cannot silently replace it with the new current interval, and its original first-claim time still controls notification retention. Normal persisted pending work already retains its original interval. Failure records use a recipient/day hash key, retain restricted recipient coordinates for recovery, and declare `expiresAt` thirty days later; deployment must verify that TTL is configured before claiming automated deletion. Failures emit aggregate counts only. Unknown checkpoint schemas and storage failures throw instead of silently resetting progress. Operators must monitor Lambda errors and `InboxDigestWorkerFailures`, inspect retained failures under existing authorized access, and correct the cause before the next automatic attempt. No automatic unbounded replay or scan is supplied.

Worker failure settlement now atomically retains the complete original pending identity, prior attempts and safe reason in both the recipient/day failure row and a durable `EXHAUSTED#` row. The latter is keyed by recipient, canonical cadence-qualified interval and strongly observed receipt-attempt stage (zero before any receipt). It has no TTL that could silently reset a terminal budget; restricted operator review/recovery and eventual cleanup are required. Three preclaim failures therefore preserve the old interval for operator recovery rather than silently retrying it with a fresh budget after quarantine. New intervals or changed cadence have distinct identities. Existing unfinished-receipt recovery remains possible only when fresh strongly consistent discovery proves receipt progress beyond that exhausted admission stage; absent progress, the same three-attempt budget cannot reset on another day or restart. Receipt progress is bounded to three claims. The day-level quarantine still applies first. The public transport scheduler is separate from this production checkpoint worker and does not establish evidence of a production queue-loss bug.

Quarantine and exhaustion reads share a complete recovery-evidence parser. Both validate the envelope, recipient/work identity, cadence and logical time, bounded counters, stable reason, worker-attempt count, canonical failure timestamp and the caller's current source shard. Failure time cannot precede its logical work or follow the trusted read clock. Quarantine additionally binds its physical key to the failure UTC day and requires the original thirty-day retention timestamp; exhaustion binds its interval/progress key and forbids a TTL. Corruption is a bodyless typed failure before candidate continuation is acknowledged, while SDK failures retain their existing typed categories. Valid restart, lost-acknowledgment and later-day recovery remain supported.

Post-claim conditional conflicts intentionally consume the documented three-attempt generation budget, separately from worker infrastructure attempts. A successful claim admits bounded current-ACL/read-state generation even if the final mutable-state fence then rejects completion. No notification commits on that rejected transaction. Attempt refunds are not introduced: they would need exact owned-token/revision proof and could otherwise refund successor work or ambiguous committed writes. SDK-condition tests exercise three failed completions and exhaustion; existing stale-owner and lost-acknowledgment tests remain the safeguards. This is a policy reassessment of the review premise, not an unqualified defect fix.

Health update の target は Project と Initiative の union です。Project は Planning entity ではないため `{teamId, projectId}` で Team-qualified に識別し、Initiative は `{entityId}` で識別します。Target ごとに update owner、週次または月次 cadence、IANA time zone、次回期限、事前 reminder、任意の期限後 escalation を設定できます。月次 cadence は設定時の local day を anchor とし、1月31日から2月末へ clamp した後も3月31日に戻します。週次 cadence は local wall-clock を維持して DST をまたぎます。

Update の publish とコメントは、Planning の書き込みと同じ transaction で audit event を保存し、Inbox 通知の outbox にします。

## Timeline と critical path

Dependency は predecessor / successor の directed edge で、self edge、重複 edge、循環を拒否する。Scheduling type は `finish-to-start`、`start-to-start`、`finish-to-finish`、`start-to-finish` の4種である。`lagDays` は signed calendar day とし、正数を lag、負数を lead として扱う。必要な場合は successor の `start` または `finish` に `on`、`not-before`、`not-after` の明示 constraint を設定できる。

Planning entity の critical path は dependency に参加する archive されていない entity の forecast（無い場合は baseline）の inclusive calendar day 数、dependency、lead / lag から DAG の最長経路を算出する。Dependency に参加しない長期 Portfolio 等が scheduling path を隠すことはない。Timeline 上の日付や dependency の変更後は、mutation response に再計算した critical path を含める。

## Work Item schedule dependency

Work Item の意味上の relation と日程を動かす dependency は別の正本を持つ。`parent` / `child`、`duplicate`、`related`、`blocks` / `blockedBy` は WorkItemConfigurationTable の Team-scoped Relation Graph が所有し、意味 relation だけでは schedule を変更しない。日程 dependency は PlanningTable が Workspace scope で所有し、両端を `{teamId, workItemId}` で識別するため、権限のある Team / Project をまたいで作成できる。

Planning snapshot は参照可能な両 endpoint が揃う edge だけを返し、同じ `workItemDependencies` と派生 summary を Table、Board、詳細 pane、Gantt、management surface が利用する。派生 summary には Work Item critical path、constraint conflict、未解決 blocker 件数、影響する Project / Milestone を含める。影響 Project は Team-qualified な `affectedProjects: {teamId, projectId}[]` だけを返し、片側だけを参照できる user へ相手 endpoint、edge、件数を漏らさない。

Dependency の作成・更新・削除は両 endpoint の manager 権限と Planning global revision を検証する。Qualified endpoint の self edge、同じ向きの重複 edge、transitive cycle、不正な lead / lag、実在しない Work Item、矛盾する constraint は commit 前に stable error code で拒否する。Work Item を削除する場合は先に incoming / outgoing dependency を解除し、dangling edge を残さない。

Schedule の move / resize / replace は、現在の Work Item revisions と Planning revision に対して downstream DAG を topological order で評価する。Preview は direct / propagated impact ごとの before / after、signed date delta、起点 dependency、conflict、影響 Project / Milestone を返す。`unscheduled` や必要な anchor を持たない `due-date` を暗黙の期間 task に補完せず、解決不能な edge は conflict として返す。評価対象は起点を含めて24件までに制限し、保存は preview 後の明示 confirm を必須とする。Confirm 時は graph と全対象 revision を再検証し、全日程を単一 transaction で更新する。Semantic `blocks` relation は preview の注意情報にはなっても propagated date update を生成しない。Automation や通常の単一 Work Item 更新は dependency を持つ日程を迂回せず、対話的な preview / confirm を要求する。

## 権限

- active Workspace member: Planning snapshot の参照
- Project / Team member: Work Item link
- Project / Team viewer: scoped versioned update history、export、watch の参照と操作
- Project / Team member: scoped update への comment、reaction の操作
- Configured update owner または Project / Team manager: manual structured update の publish
- Project / Team manager: scoped entity、Work Item schedule dependency、Cycle rollover、archive / duplicate / move
- Workspace owner / admin: Workspace scope の Portfolio / Roadmap 等の管理
- guest: mutation 不可

Move、dependency、link では起点と終点の両方を検証します。Move は対象 entity と active な全子孫の Team / Project scope を一つの transaction で変更し、archive 済み子孫は履歴上の scope を保持します。Project / Team member は、アクセス可能な Work Item を Workspace scope の戦略 Goal / OKR に link できます。Workspace scope の構造変更は owner / admin に限定します。Entity owner は active Workspace member に限り、member の無効化前に所有 entity を移譲または archive する必要があります。Active entity または保存済み Work Item link が参照する Team / Project の archive は、entity を移動または archive し、link を解除するまで拒否します。権限確認に失敗した場合、Planning store の mutation は呼び出しません。
