# 0001. 設計判断を ADR として記録する

- 状態: 採用
- 日付: 2026-11-19
- 関連: Issue #366

## 背景

`docs/` の各文書は storage key、transaction、上限値などの現在の契約を詳しく書いているが、
なぜその構成を選んだか、どの選択肢を退けたかは Issue や PR の議論に散らばっている。
新しい開発者やコーディングエージェントが設計を変えるとき、過去の判断の前提を確認する手段がない。

## 決定

- 設計判断を `docs/adr/NNNN-*.md` に1判断1ファイルで記録する。
- 書く対象と書き方は [`docs/adr/README.md`](README.md) に従う。
- 採用後の ADR は書き換えず、判断を変えるときは新しい ADR を作って古い方を置き換え済みにする。
- 現在の契約は引き続き `docs/*.md` に書き、ADR からはそれを参照する。

## 検討した選択肢

- Issue / PR の議論だけに残す: 追加作業はないが、検索しにくく、決定と却下理由が埋もれる。
- `docs/*.md` に「経緯」節を足す: 契約と経緯が混ざり、現在の仕様が読みにくくなる。
- ADR を別ディレクトリに分ける（採用）: 契約と経緯を分けられ、番号で参照できる。

## 結果

- 設計を変える PR のレビューで、前提となった判断を ADR 番号で参照できる。
- 書く手間が増えるため、対象は README の「いつ書くか」に限定する。
- 開発規約の本体である `AGENTS.md` にも ADR を書く条件を追記する。`AGENTS.md` は review の
  trust root のため、追記は maintainer が別途行う（[CONTRIBUTING.md](../../CONTRIBUTING.md) から参照済み）。
