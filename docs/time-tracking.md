# Time tracking, timesheets, and budgets

Time tracking is scoped by Workspace and Team. A time entry references a canonical Work Item and may optionally reference a Project. Indirect work, such as a meeting, has no Work Item and always carries a work category (see [Indirect work](#indirect-work-without-a-work-item)). Manual entries and timer-generated entries share the same lifecycle:

`draft → submitted → approved → locked`

Rejected entries return to `rejected` and can be edited and submitted again. A manager can also send an approved or locked entry back to `rejected` with a required reason (`return`); its history records the `returned` action with the reason, and `approvedAt` / `lockedAt` are cleared. Every create, edit, submit, approve, reject, and lock operation writes an immutable history record and a shared audit event in the same transaction. Deleting a draft or rejected entry writes a `time-entry.deleted` audit event in the same transaction as the delete; the entry's history records are kept. Budget changes also append a shared audit event in the same transaction. Estimates are not stored here: the canonical estimate is the Work Item's `schedule.plannedEffortMinutes` (see [Work Items](work-items.md#estimate-remaining-effort-and-progress)), and summaries and timesheets read it from the Work Items, including archived ones, so archiving finished work keeps its estimate next to its recorded time. Entry revisions are checked with optimistic concurrency, and timer stop atomically removes the running timer while creating the entry, its history, and its audit event.

## HTTP surface

- `POST /api/teams/:teamId/time-entries` creates a manual draft.
- `GET /api/teams/:teamId/time-entries` lists entries in the caller's Project allowlist and entries without a Project, narrowed by the manager scope below.
- `PATCH /api/teams/:teamId/time-entries/:entryId` edits a draft or rejected entry.
- `DELETE /api/teams/:teamId/time-entries/:entryId?expectedRevision=N` deletes the caller's own draft or rejected entry and returns `204`. Only the entry owner may delete, with Team member permission and, when the entry has a Project, member access to that Project; managers reject time instead. The Work Item is not checked, so a draft whose Work Item was deleted can still be deleted. Submitted, approved, and locked entries return `409 TimeEntryNotDeletable`, and a stale revision returns `409 TimeEntryRevisionConflict`. The owner's Workspace membership version (and the Enterprise control revision, when present) is rechecked in the delete transaction, so a member whose access was removed after the route's check gets `409 TimeEntryAuthorizationChanged` and nothing is deleted.
- `POST /api/teams/:teamId/time-entries/:entryId/{submit,approve,reject,lock}` changes one lifecycle state.
- `POST /api/teams/:teamId/time-entries/:entryId/return` sends an approved or locked entry back to `rejected`; `reason` is required.
- `GET /api/teams/:teamId/time-periods` lists the Team's closed months with `canManagePeriods` (the caller may close and reopen this Team's months); `POST /api/teams/:teamId/time-periods/:month/close` closes a `YYYY-MM` month in the body's `timeZone` (default `UTC`); `POST /api/teams/:teamId/time-periods/:month/reopen` reopens it with a required `reason`. See [Month close](#month-close).
- `GET /api/time-periods/:month` lists every Team of the Workspace with its close of the month; `POST /api/time-periods/:month/close` (body `timeZone`, default `UTC`) and `POST /api/time-periods/:month/reopen` (required `reason`) close or reopen the month for every Team. See [Workspace-wide close](#workspace-wide-close).
- `POST /api/teams/:teamId/timesheet/{submit,approve,reject,lock}` applies a lifecycle operation to all eligible entries in a period. The operation is resumable: every eligible entry is attempted, and `failedEntryIds` plus `partialFailure` identify entries that need a later retry.
- `POST /api/teams/:teamId/timers` starts the caller's timer; `GET /api/time-tracking/timers/active` supports offline recovery; `POST /api/time-tracking/timers/:timerId/stop` creates a draft from the timer; `DELETE /api/time-tracking/timers/:timerId` discards an overlong or unwanted timer.
- `GET /api/teams/:teamId/timesheet` returns daily rows and weekly rows that start on the Workspace week start day (Monday when unset), using the requested IANA timezone. `groupBy=week` reports use the same weeks. `canManageTeam` tells whether the caller manages time in the Team, and so which entries the rows total (see [Who sees which time](#who-sees-which-time)).
- `GET /api/time-tracking/my-timesheet` returns, for every Team the caller can view, the caller's own timesheet rows (`canManageTeam` is always `false`, so only their own time) and their own entries in the period, without money fields. It takes `from`, `to`, and `timeZone` like the Team timesheet.
- `POST /api/time-tracking/my-timesheet/submit` submits the caller's own entries in `from`–`to` named in `entries` (1 to 500 `{ teamId, entryId, expectedRevision }`, the draft and rejected entries the member saw) across the Teams where the caller is a member (Workspace guests are rejected). Only the named entries are submitted, each at the revision given, so time added since is left alone. Each entry goes through the same transition as `POST /api/teams/:teamId/timesheet/submit`, so it enters its Team's own approval. With `Idempotency-Key`, each entry's transition uses a key derived from it, Team, and entry, so a retry after a lost response replays the first result; an entry named in a Team the caller cannot submit to, or not found among the caller's entries, is reported as failed. The response totals `count` and `failedEntryIds` and lists them per Team in `teams`; a failed entry is retried by submitting again. A Team that cannot be processed at all, for example because the caller just lost access to one of its Projects, is reported with `failed: true` and does not stop the other Teams; `partialFailure` is then `true`.
- `GET /api/teams/:teamId/time-tracking/summary` groups actual minutes by day, week, user, Project, Work Item, or work category (`groupBy=category`).
- `GET /api/teams/:teamId/time-tracking/export` exports the same ACL-filtered summary as CSV.
- `PUT /api/teams/:teamId/time-budget` and `PUT /api/teams/:teamId/projects/:projectId/time-budget` store optimistic-concurrency-protected budgets. A budget carries its `teamId`; a Project budget is stored under `TIME_BUDGET#project#<teamId>#<projectId>` because Project IDs are unique only within their Team, and a Team budget under `TIME_BUDGET#team#<teamId>`.
- A budget per period is saved with the same `PUT` plus `periodBudget: true`, `periodFrom`, and `periodTo`, under `...#PERIOD#<from>#<to>` next to the scope's default budget ([ADR 0077](adr/0077-time-budget-per-period.md)). Saving the same period replaces it at the expected revision; a period overlapping another budget per period of the scope is rejected with 409 `TimeBudgetPeriodOverlap`, and a scope holds at most 40 (409 `TimeBudgetPeriodLimit`). `DELETE /api/teams/:teamId/time-budget/periods/:periodFrom/:periodTo?expectedRevision=N` and the same path under `/projects/:projectId` delete one (204, 404 when missing, 409 on a stale revision). The optional `expectedUpdatedAt` query, and the same field in the `PUT` body, also names the save time read, so a delete or save read before the period was deleted and saved again, which restarts at the same revision, is rejected with 409.
- With `budgetScope`, the summary returns as `budget` the scope's budget per period whose period equals `from`–`to` exactly, or else the default budget, and lists the scope's budgets per period in `budgetPeriods`. The Project budget report keeps using the default budget.
- `GET /api/teams/:teamId/projects/:projectId/budget-report` and `.../budget-report/export` (CSV) return the Project budget against actual report with earned value figures. See [Project budget report and earned value](#project-budget-report-and-earned-value).
- `GET|POST /api/teams/:teamId/projects/:projectId/expenses`, `PUT|DELETE .../expenses/:expenseId`, and `POST .../expenses/:expenseId/decision` list, submit, resubmit, delete, and approve or reject Project expenses. See [Project expenses](#project-expenses).
- `GET /api/teams/:teamId/time-entry-policy` returns the Team's overlap and daily total checks with `canEdit`; `PUT` saves them. See [Overlap and daily total checks](#overlap-and-daily-total-checks).

All period endpoints require `from`, `to`, and accept `timeZone` plus `groupBy`. Date-only ranges are interpreted as local dates and converted to UTC before querying. Intervals crossing midnight are split at timezone-aware local boundaries, including daylight-saving transitions.

## Work categories and date-and-minutes entries

An entry may carry a `category`: `design`, `implementation`, `review`, `meeting`, `management`, `training`, or `leave`. Create and `PATCH` accept it, and `PATCH` with `category: null` removes it. Entries without one, including every entry saved before categories existed, are reported in the `uncategorized` group (label `Uncategorized`) of a `groupBy=category` summary or CSV export. Workspace owners and admins can rename these, add their own, and retire categories (ADR 0047); `GET /api/workspace/time-entry-categories` returns the list. A create must use a category the Workspace still offers, or it is rejected with `400 InvalidTimeEntryCategory`. A `PATCH` checks the category only when it changes it: an entry can be edited while it keeps a category that has since been retired, but moving it to a retired or unknown category gets the same `400`.

Instead of `startAt` and `endAt`, a create or `PATCH` request may send `date` (`YYYY-MM-DD`), `minutes` (a whole number from 1 to 1440), and optionally `timeZone` (IANA, default `UTC`). The server stores the entry from local midnight of that date for that many minutes and marks it `durationOnly: true`, so clients know its times of day carry no meaning. The minutes must end within the local date, so a 23-hour daylight-saving day accepts at most 1380. Sending both forms is rejected. A `PATCH` that sends `startAt` and `endAt` keeps a date-and-minutes entry as one when they repeat the stored interval, so a client that always sends the times does not change it; different times turn it into a timed entry. Timers still record times of day.

## Overlap and daily total checks

Each Team chooses, for overlapping time and for a daily total limit, whether a save is not checked (`off`), saved with a warning (`warn`), or refused (`reject`); see ADR 0048. A Team that has saved nothing uses `off` for both with a limit of 600 minutes. `GET /api/teams/:teamId/time-entry-policy` returns `{ policy: { overlap, dailyLimit, dailyLimitMinutes, teamId, revision, updatedAt? }, canEdit }` to Team viewers. `PUT` takes `{ overlap, dailyLimit, dailyLimitMinutes, expectedRevision }` (`dailyLimitMinutes` 1 to 1440), is limited to managers of the whole Team (`403 TimeEntryPolicyDenied`), returns `409 TimeEntryPolicyRevisionConflict` for a stale revision, and records the `time-entry-policy.updated` audit event.

Create and `PATCH` of an entry apply the checks; `PATCH` only when `startAt` or `endAt` changes. The entry is compared with every other entry of the same member in the Team, whatever its state. Days are local days in the Workspace time zone (the calendar setting's `timeZone`, `Asia/Tokyo` when the Workspace has not chosen one), and an entry crossing midnight is split between the days it covers the way reports split it. Date-and-minutes entries count toward daily totals but never overlap. A `reject` check returns `409 TimeEntryOverlap` or `409 TimeEntryDailyLimitExceeded`. A `warn` check saves the entry and adds `warnings` to the response, such as `{ code: 'TimeEntryOverlap', entryIds }` or `{ code: 'TimeEntryDailyLimitExceeded', date, minutes, limitMinutes }`; the field is absent when nothing was broken. Only the entry's owner receives warnings; a manager editing another member's entry gets none, since the check covers time in Projects that manager may not see. Entries a timer creates are not checked. The check reads the date index, so two entries saved at the same moment may both pass.

## Indirect work without a Work Item

A create request may omit `workItemId` to record indirect work, such as a meeting. It then requires a `category` (`TimeEntryCategoryRequired` otherwise) and may name a `projectId`. Authorization follows the same rule as a Work Item without a Project: with a `projectId` the caller needs member access to that Team Project (manager access to set a rate); without one, Team member permission is enough. `PATCH` accepts `workItemId: null` to turn a Work Item entry into indirect work (its Project stays unless `projectId` changes it, and a category is required), changes the Project of indirect work with `projectId` (`null` removes it), and accepts a `workItemId` to attach the time to a Work Item, which then takes the Work Item's Project.

Indirect entries go through submit, approval, summaries, timesheets, and CSV export like any other entry. A `groupBy=work-item` report puts them in the `no-work-item` group (label `No Work Item`), and they add no estimate. Who sees and approves entries without a Project is the rule for Project-less entries in [Write access and manager scope](#write-access-and-manager-scope); entries with a Project follow that Project. Capacity planning counts their minutes in the member's daily actual time but not against any Work Item.

Mutation endpoints accept an optional `Idempotency-Key`; when supplied, the shared durable receipt store binds it to the actor, operation, and request fingerprint, then replays the stored result for an equivalent retry. An in-progress duplicate receives a stable conflict response.

## Month close

A Team manager closes a calendar month so its time stops changing. The close stores the month and the IANA timezone that defines its first and last instant. While it exists, any create, edit, delete, timer stop, or lifecycle transition whose entry interval overlaps the month fails with `409 TimePeriodClosed`; an edit is checked against both the stored and the new interval, so time cannot be moved into or out of a closed month. Locking an approved entry is still allowed, because that is how a closed month is finalized. The Web shows a 409 `TimePeriodClosed` as "this month has been closed" instead of a revision conflict. Closing a month twice fails with `TimePeriodAlreadyClosed`. A month must be between `1970-01` and `9998-12` (`InvalidMonth`).

Reopening requires a non-empty `reason` and removes the close. Both operations write a shared audit event (`time-period.closed` / `time-period.reopened`, entity `time-period`, `teamId:month`) in the same DynamoDB transaction, and the reopen reason is kept in the event metadata. Closes are stored in the time tracking table under the `TIME_CLOSE#<teamId>#<YYYY-MM>` sort key.

Only a caller who manages every Project of the Team (a system administrator or a direct enterprise Team grant with `teams.manage`) may close or reopen; a manager of only some Projects receives `TimePeriodCloseDenied`. Every member of the Team can list the closed months.

The entry write transaction also rechecks the close row of every month its intervals can touch in any timezone, so a close or reopen that lands between the check and the write cancels the write with `409 TimePeriodClosed`; the client reloads and retries.

The Web **Month close** view of the Team time tracking page lists the closed months, closes a month in the member's display timezone (the browser's when none is saved), and reopens one with a reason. The approval view lists approved and locked entries with **Return**, which calls the `return` action with a reason.

### Workspace-wide close

A Workspace owner or administrator, or a system administrator, may close or reopen the same month for every Team of the Workspace; under an Enterprise assignment the caller needs `workspace.manage` at the Workspace instead of the legacy role. Anyone else receives `403 WorkspaceTimePeriodCloseDenied`. The Web screen is **Settings → Workspace → Month close for every Team**, shown when `/api/auth/me` returns `canManageWorkspaceTimePeriods`, so it needs no access to any Team; `GET /api/time-periods/:month` returns each Team's `name` from the Workspace directory. Each Team's write is fenced by the caller's Workspace membership: if it changes during the run, the remaining Teams are reported as `failed` and not changed, and each failure is logged with the request's correlation ID. The routes do not add a Workspace row: they apply the Team close or reopen above to each Team of the Workspace directory, one Team at a time, so the entry write checks, audit events, and `TIME_CLOSE#<teamId>#<YYYY-MM>` rows stay the same. The month and timezone are validated before any Team changes.

The response lists each Team with `closed` or `reopened` when the request changed it, `already-closed` or `not-closed` when it was already in that state, and `failed` when it needs a retry, plus `partialFailure`. A retry changes only the Teams left over. A Team created after the close is not closed; its managers close it on the Team route. The Workspace routes take no `Idempotency-Key`, because a repeat is reported as `already-closed` or `not-closed` instead of changing anything.

## Project budget report and earned value

`GET /api/teams/:teamId/projects/:projectId/budget-report?from=YYYY-MM-DD&to=YYYY-MM-DD&timeZone=<IANA>&interval=day|week` returns a `ProjectBudgetReport` (`@mukuroji/contracts`). Only a Project manager may read it (a system administrator, a direct Team grant, or the manager role on that Team Project); others get `403 ProjectBudgetForbidden`, and a Project outside the Team or without any role gets `404 ProjectNotFound`. `timeZone` defaults to `UTC` and `interval` to `day`; a range with more than 400 days (or 400 weeks) is `400 InvalidProjectBudgetReportRequest`. Nothing is stored: the report is calculated on each read from the Project budget, the active schedule baseline, the current Work Items of the Team (archived ones included), and the time entries of the Project. The decisions behind the rules are in [ADR 0065](adr/0065-project-budget-report-and-evm.md).

- `asOf` is today in `timeZone`, clamped to `from`..`to`; when today is before `from`, `asOf` is `from` and no actuals are counted. Actual minutes and cost count entries of the Project in every status, including time on canceled Work Items, by local date from `from` through `asOf`; an entry that crosses midnight is split between the days the way time reports split it, and its cost follows the minutes. `uncostedMinutes` are minutes of entries without a rate. `actualCostByCurrency` keeps the time cost of every currency.
- Approved [Project expenses](#project-expenses) dated `from` through `asOf` are in `approvedExpenseByCurrency`, and the ones waiting for a decision in `pendingExpenseByCurrency`. The budget currency's approved expenses are added to the actual cost: the points' `actualCostMinor`, `earnedValue.money.actualCostMinor`, and `budgetConsumedPercent`, which uses only the budget currency. Expenses never change the minutes.
- BAC is the sum of the baseline's `plannedEffortMinutes`, leaving out Work Items that are canceled now (`canceledEffortMinutes`). PV spreads each baseline Work Item's effort evenly over the calendar days from its planned start to its planned end; one with only an end date plans everything on it, and one without an end date plans nothing (`unscheduledEffortMinutes`). EV is each baseline Work Item's effort times its current progress under the Team `progressMode`; a deleted Work Item, or one that now belongs to another Project, earns nothing. SPI = EV / PV, CPI = EV / AC, EAC = BAC / CPI, ETC = EAC − AC, VAC = BAC − EAC; an index whose divisor is zero is omitted. Time logged with nothing earned yet gives a CPI of 0, and EAC, ETC, and VAC are then omitted. `earnedValue` is `null` without a baseline or without baseline effort.
- With a budget, `earnedValue.money` repeats the figures in the budget currency: PV and EV are the effort figures times the budget amount per baseline minute, AC is the actual cost in the budget currency, and EAC is the budget divided by the money CPI.
- `points` holds one cumulative point per day or Monday-based week (clipped to the range) with PV in minutes and, with a budget, in money; actual minutes and cost are absent for buckets that start after `asOf`. EV is not reconstructed for past dates.
- When the Workspace counts coding agent cost ([ADR 0119](adr/0119-agent-cost-in-project-budgets.md), below), `agentCost` reports the estimated cost of the Agent Runs that finished from `from` through `asOf` on Work Items the Project holds now, by the local date they finished. The cost stays in US dollars and is never converted. For a USD budget (`status: 'included'`), `amountMinor` in cents (each day's total rounded once) is added to the actual cost like an approved expense: the points' `actualCostMinor`, `earnedValue.money` (AC, CPI, EAC, ETC, VAC), and `budgetConsumedPercent`. For a budget in another currency (`status: 'separate-currency'`) only `estimatedCostMicroUsd` is reported beside the actual cost and nothing is added. Runs that finished outside the local date range do not count toward the limit. A report reads at most 1,000 runs with a cost, newest first across failed and other runs, and 100 finished-run index pages; past that, `truncated` is `true` and the amount is a lower bound. A report period that starts after today reads no runs. The daily alert finds the Project's Work Items in at most 200 pages of the Team's Work Items; a Team with more fails that Project's check instead of counting part of them, while the other Projects of the Workspace are still checked and the run fails afterwards. `agentCost` is absent when the Workspace does not count the cost, the report has no budget, or the deployment has no Software factory.
- The CSV export starts with a summary row (budget, BAC, PV, EV, AC, SPI, CPI, EAC in minutes and money, approved and pending expenses in the budget currency, and the Agent Run cost added to a USD budget in cents, the cost in millionths of a US dollar, and whether it is a lower bound) followed by one row per point.

### Coding agent cost in Project budgets

A Workspace administrator sets `agentCost` in `PATCH /api/tenant/profile` ([ADR 0119](adr/0119-agent-cost-in-project-budgets.md)): `{ "includeInProjectBudgets": true }` (default `false`); anything but a boolean flag answers `400 InvalidTenantAgentCostSettings`. There is no exchange rate. When the setting is on, every budget report shows the Project's Agent Run cost in US dollars, and a USD budget adds it to the report, its earned value money figures, and the daily budget threshold alert alike; the alert of a budget in another currency reads no runs. The Team portfolio and the Analytics earned value metrics (in minutes) do not add it. The budget report shows only the Project total, to those who may read the report (the Project managers, the Team managers, and Workspace administrators).

Analytics metrics and widgets for earned value, and the PMO dashboard widget are still open in #345. Budget threshold notifications and the Automation trigger are described in [ADR 0105](adr/0105-project-budget-threshold-alerts.md).

## Project expenses

Costs other than time, such as subcontracting or licenses, are Project expenses (`ProjectExpense` in `@mukuroji/contracts`, [ADR 0104](adr/0104-project-expense-entries.md)). Only a Project manager may read or change them, with the same check as the budget report (`403 ProjectExpenseForbidden`, `404 ProjectNotFound`).

- `POST .../expenses` takes `date`, `category` (up to 80 characters), `amountMinor` (a positive integer in minor units), `currency`, and optionally `description`, `workItemId` (a Work Item of the Project), and `receiptFileIds` (up to 5 File IDs of the Project's files). The expense starts `submitted`, and its ID comes from the `Idempotency-Key`, so a retry returns the same expense. Its audit changes record that `amountMinor`, `category`, `description`, and the decision note changed, without their values, so an audit reader who cannot manage the Project does not see the cost.
- `POST .../expenses/:expenseId/decision` with `outcome` (`approved` or `rejected`), an optional `note`, and `expectedRevision` decides a submitted expense. The manager who submitted it gets `403 ProjectExpenseSelfDecisionForbidden`; another Project manager must decide.
- `PUT .../expenses/:expenseId` replaces a submitted or rejected expense and submits it again under the caller; `DELETE .../expenses/:expenseId` with `expectedRevision` removes it, and a retry of that request with the same `Idempotency-Key` after a lost response answers `204` again. A late retry of the original `POST` after the delete answers `409 ProjectExpenseDeleted` instead of bringing the expense back. An approved expense answers `409 ProjectExpenseApproved` to both.
- A Project holds at most 2,000 expenses (`413 ProjectExpensesFull`). Only approved expenses count toward the budget report.
- The Team portfolio (PMO dashboard) adds the approved expenses dated within the budget period up to today to each Project's `actualCostMinor`, so its budget use includes them; an approved expense in another currency sets `hasOtherCurrencyCost`.

## Budget threshold alerts

A Project's default budget takes `alertPercent` (a whole number from 1 to 1000, default 90) in the same `PUT .../projects/:projectId/time-budget` ([ADR 0105](adr/0105-project-budget-threshold-alerts.md)). A save that omits it keeps the stored value; a Team budget or a budget per period answers `400 InvalidBudgetAlertPercent`.

Once a day, in the 9:00 run of the notification schedule (Asia/Tokyo, the clock the timesheet reminders use), each active Project with a budget is measured the way the budget report counts cost: time cost plus approved expenses in the budget currency, plus the converted Agent Run cost when the Workspace counts it ([ADR 0119](adr/0119-agent-cost-in-project-budgets.md)), from the period start (or the first record without a period) through today or the period end. At or past `alertPercent`, the schedule writes one `project-budget.threshold-reached` audit event whose ID comes from the Workspace, Project, budget period, amount, currency, and threshold, so later runs are duplicates until one of them changes. The event carries the percentages only (`budgetThresholdPercent`, `budgetConsumedPercent`), never an amount.

The alert notifies the charter owner when they manage the Project, or else every Project manager (reason `budget-threshold`). A Project manager is a manager member of the Project or a member whose direct Enterprise role assignment grants `projects.manage` on the Project or its Team; a role assigned to a directory group is not resolved, because group membership is known only from a member's sign-in. The event carries no amounts, and a recipient who no longer manages the Project when the notification is delivered is skipped. For a member whose access an Enterprise role decides, that check asks for `projects.manage` on the Project, as the budget report and expense endpoints do, so a manager row left behind after the role changed does not count. The daily check narrows the managers by the same rule, and when the charter owner no longer manages the Project, or their standing depends on directory groups known only from a sign-in, every other manager is told. The percentages are in the notification message only; the audit event summary names no figures. The same event fires the `budget-threshold` Automation trigger ([Automation](automation.md#budget-threshold-trigger)).

## Write access and manager scope

Workspace guests have read-only access: every non-`GET` time tracking route (entries, timers, timesheet actions, and budgets) rejects them with `WorkspaceRoleDenied`, whatever Project role they hold.

Managing time is decided per Project, not per Team. A caller who manages one Project of a Team can edit other members' entries, list their entries and history, run the week-wide approve / reject / lock actions, and read a Project budget only for the Projects they manage; approving, rejecting, or locking a single entry also requires managing its Project. Moving an entry while editing another member's time, or changing a rate, requires managing both the current and the new Project. The Project is the one stored on the entry, not the current Project of its Work Item. Entries without a Project (time on a Work Item that is not in a Project) belong to the Team: anyone who manages time in the Team, that is, manages at least one of its Projects or holds a direct Team grant, can edit, list, read the history of, approve, reject, lock, and read the costs of other members' entries without a Project, the same scope that may correct actual dates on a Work Item without a Project. The authorization is bound to the entry revision it read, so a request that expects a newer revision fails with `TimeEntryRevisionConflict`. A direct enterprise Team grant with `teams.manage` manages every Project of the Team.

## Who sees which time

| Caller | Own entries | Other members' entries in a Project | Other members' entries without a Project |
| --- | --- | --- | --- |
| Member (no manager role in the Team) | In visible Projects and without a Project | No | No |
| Team time manager | In visible Projects and without a Project | Only in the Projects they manage | Yes |
| System administrator | All | All | All |

The entry list, the week-wide timesheet actions, and the summary, timesheet, and CSV export reports all follow this table, so a member's timesheet totals only their own time and never the Team's. One exception: a summary or CSV export grouped by Work Item (`groupBy=work-item`) totals every member's time in the caller's visible Projects and outside Projects, because anyone who can see a Work Item compares its estimate with its actual time (the Work Item detail 工数 section reads it). Costs stay limited to managers either way. Summary and timesheet responses carry `canManageTeam`; the Web reads it, not `costsRedacted`, to decide whether to show the approval queue, and the 集計 view tells members that it totals only their own time.

## Confidential cost fields

Members can record billable status and duration but cannot set or read `hourlyRateMinor` or `actualCostMinor`. The API resolves the caller's Work Item Project assignment before persisting an entry and filters reports by the caller's Project allowlist. Confidential money fields are evaluated against the Projects the caller manages for each entry; only authorized managers receive them in entry, summary, and export responses. Mixed-currency reports expose currency-keyed totals rather than combining minor units.

## Rate cards and the Workspace currency

Each Team has one rate card (`TIME_RATE_CARD#<teamId>`, [ADR 0054](adr/0054-team-time-rate-card.md)): a currency, member rows (an own hourly rate, a job role, or both), and job role rows (a job role ID from the Work Item configuration and its hourly rate). An entry created, or a timer stopped, without `hourlyRateMinor` takes the member's own rate, else the rate of the member's job role, and then the card's currency. A rate a manager types wins over the card, and saved entries keep the rate they were created with. `GET` / `PUT /api/teams/:teamId/time-rate-card` (whole-card replace with `expectedRevision`, audit `time-rate-card.updated` with the rows redacted) are limited to managers of the whole Team (`403 TimeRateCardDenied` otherwise). `GET /api/teams/:teamId/time-tracking/settings` tells any Team viewer the Workspace currency and whether they may manage the card.

The tenant profile's `defaultCurrency` (owner / admin, `PATCH /api/tenant/profile`, a known ISO 4217 code) is used when an entry, timer stop, or budget request names no currency and no rate card rate applies (a rate from the card always brings the card's currency); the Workspace default is not part of the idempotency fingerprint, so a retry after the setting changes still replays; a Workspace that has not saved one uses `JPY`. Amounts stay in minor units of their currency, which for JPY is whole yen.

Production time-entry persistence uses the existing analytics DynamoDB table with distinct `TIME_*` sort-key prefixes, while lifecycle audit events use the shared audit events table. The API role grants item-level transaction access to both tables, while existing Analytics rows remain unchanged. Money fields may exist in internal audit snapshots for redaction, but `amountMinor` is excluded from the audit diff and confidential entry cost fields are not copied into entry snapshots.

## Web screens

- **Work Item detail → 工数 section** (`time` in a Work Item Type's `detailSections`, included in the default type): shows the Work Item's canonical estimate next to the Team's actual minutes for the last year (from the `work-item` summary) and the remaining effort (the recorded remaining effort, otherwise the estimate minus actual), lets a member start / stop / discard their timer (restored from `GET /api/time-tracking/timers/active` after a reload or reconnect), and add, edit, and submit their own entries from the last 90 days. A timer older than the 7-day entry limit can only be discarded. The estimate and remaining effort are edited in the Work Item's schedule section, not here.
- **Team → 工数** (`/teams/:teamId/timesheet`): the member's week (starting on the Workspace week start day, Monday when unset) as a Work Item × day table and per-day entries, with week-wide submit, rejection reasons from the entry history, and resubmission. `?week=YYYY-MM-DD` selects the week. **間接作業を追加** records indirect work as a category, a Project, a date, and hours (sent as date and minutes in the browser's timezone); the table shows it as one row per category. The Projects offered are the Team Projects in the task-view write scopes, and **プロジェクトなし** appears only with the Team scope. Editing indirect work that was recorded with start and end times keeps them unless the date or hours change; the form then omits `date` and `minutes` from the `PATCH`. Draft and rejected entries have **削除** with an inline confirmation.
- **Team → 工数 → 週報** (`?view=weekly-report`, #348): drafts the member's weekly report for the selected week from facts the member can already read. Work Items come from `GET /api/work-items?teamId=…&involvement=mine` (owned or contributed, filtered by the server), time from the member's own entries in the week. Completed = `actualEndDate` in the week; started = `actualStartDate` in the week and not completed in it; overdue = open with a planned end before today (current week) or before the week's end (past weeks); next week = other open items in progress or planned to start or end by the end of next week; recorded time is totalled per Work Item. The member adds issues and a reflection and copies the report as Markdown in the 今週やったこと / 来週やること / 課題 layout. The member can save the notes (`PUT /api/teams/:teamId/weekly-reports/:memberKey/:weekStart/draft`, revision CAS) and submit a version (`POST …/submissions`, `expectedSubmissionCount` and `expectedRevision` CAS, Idempotency-Key aware). A submission sends only Work Item IDs and minutes per section; the server reads each Work Item with the author's permissions, drops those the author cannot read, and stores key, title, Project, and planned end. Indirect work references no Work Item, so it is sent as `indirectTime` rows of work category and minutes (one per category), stored as sent, and shown to every reader of the version; versions stored before this field read as having none. Submitted versions are immutable; resubmitting adds a version (at most 10 per week). Reads (`GET …/:memberKey/:weekStart`, `GET …/:memberKey` history) filter every Work Item by the reader's current Project access (and, under Enterprise roles, `work-items.read` at the Work Item's Project or Team): one the reader cannot view comes back as `{ hidden: true, minutes }`. Only the author sees the saved notes. A Team manager (system administrator, Workspace owner / admin without Enterprise roles, Enterprise `teams.manage`, or manager of a Project the author belongs to in that Team) reads submitted versions, and `GET /api/teams/:teamId/weekly-reports?weekStart=` lists the submission state of the members of the Projects the caller manages (**週報の提出状況**, `?view=team-weekly-reports`). Storage and visibility are decided in [ADR 0030](adr/0030-weekly-report-storage-and-visibility.md). **週次まとめ** (`?view=weekly-summary`, #631): `GET /api/teams/:teamId/weekly-summary?weekStart=` summarizes a week for any Team viewer. The server reads the Team's non-archived Work Items (at most 20,000 rows, else 413), keeps those the reader may read (Project access, and `work-items.read` under Enterprise roles), and reports per readable Project (in Team order, then a scope without `projectId` for Work Items outside any Project): completed (`statusCategory` completed and `actualEndDate` in the week), delayed against the Project schedule baseline (completed in the week after the baseline end, or open with a current planned end after it; `delayDays` is the difference), overdue (open with a planned end before the day after the week, or before today in the Work Item's calendar while the week runs), and Milestones reached (`schedule.mode` milestone and completed in the week). Each section returns its full `count` and at most 50 items. Status and dates are read as they are now, not reconstructed for past weeks. Planning Milestone entities are not counted. The view copies the summary as Markdown (only what the reader's response holds). **月次まとめ** (`?view=monthly-summary&month=YYYY-MM`, #348): `GET /api/teams/:teamId/monthly-summary?month=YYYY-MM` applies the same reads, access rules, and section rules to the calendar month (`periodStart` the 1st, `periodEnd` the last day; a month after next month in UTC is 400) and adds `previousTotals`, the counts of the month before over the same Work Items, also judged by their current state. Scheduled monthly delivery of figures is the Analytics report schedule (`frequency: monthly`, [analytics.md](analytics.md)).
- **Team 横断の稼働 → 自分の工数（全 Team）** (`/workload`): one week table with a row per Team (the member's own minutes per day, total, and the number of draft and rejected entries) and **全 Team の下書きをまとめて提出**, which calls the submit across Teams and reports partial failures. The week follows `?week=YYYY-MM-DD`.
- **Team → 工数 → 承認** (`?view=approvals`): Team managers see submitted entries grouped by member with approve / reject (reason required) and approved entries with lock, plus week-wide approve and lock that report `failedEntryIds` for a retry. Whether the viewer manages the Team is read from the Team timesheet's `canManageTeam` flag; other members see a permission notice. The screens never display confidential rates or costs.

The entry list endpoint returns at most 500 entries with no cursor, so the Web reads a busy period page by page, continuing from the start of the last entry and skipping repeats. If a page brings nothing new, or 20 pages are not enough, the screen says the list is partial and the approval queue turns off week-wide approve and lock so they cannot touch entries the manager has not seen. Entries that cross local midnight count on each day they cover in whole minutes, allocated like the server timesheet (floor per day, leftover minutes to the largest fractions), and an entry carried over from Sunday is listed on the next week's Monday. The Work Item panel's 90-day window moves forward at local midnight, and a failed Work Item or member lookup on the time tracking page is shown with a retry instead of an empty task list. Manual entry offers only tasks the server would accept, using the write scopes the Team task-view list returns (the same server-effective permissions, enterprise grants included): a task in a Project needs that Team-qualified Project scope, and a task without a Project needs the Team scope. When no task qualifies, Add manually is turned off and the page says why. The entry form has a separate end date, so editing an overnight entry keeps both days.

One limit to keep in mind when rolling this out:

- A Work Item Type saved before this change keeps its stored `detailSections`, so the 工数 section stays hidden on that Type until an admin adds `time` in the Type settings. Only the default Type and new Types include it automatically. No data migration was done.

Members whose draft or rejected entries stay unsubmitted get a daily-checked Inbox reminder; the number of days is a Team and personal notification setting (see [Notifications](notifications.md#工数の督促)).

Every Web mutation sends an `Idempotency-Key`. A request that does not reach the API, an in-progress duplicate, or a 5xx keeps the same key so repeating the action after reconnecting cannot record it twice; a revision conflict reloads every time tracking query before the member retries. Team and Project budgets are edited in the 集計 view; the Project budget report is on the Project overview.
