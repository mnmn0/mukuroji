# 管理者ガイド

Workspace の owner・admin、Team の管理者向けに、メンバーと権限、業務の設定、自動化、
coding agent の受け入れ、Enterprise のセキュリティ設定をまとめます。管理系の画面は
サイドバーの **設定**（`/settings`）と **ID・セキュリティ**（`/settings/security`）に集まっています。

**設定** は3つの区分に分かれ、それぞれ URL で直接開けます。

| 区分 | URL | 主な内容 |
| --- | --- | --- |
| 個人 | `/settings/personal`（`/settings` も同じ） | 表示設定、通知設定、サインインとセキュリティ、AI の利用、agent の接続 |
| Workspace 管理 | `/settings/workspace` | アクセス台帳、ID・セキュリティ管理への入口、テナント管理、チームとプロジェクトの管理、API と外部連携、オートメーション |
| Team | `/settings/team` | ワークフローとフィールド、Work Item key の prefix、エージェント設定 |

区分は画面の分け方だけで、操作できる範囲はこれまでどおりロールで決まります。

## 権限のしくみ

mukuroji の権限は Workspace と Project の2段階です。Team には独立したメンバー登録がなく、
**Team のメンバー = その Team に属する Project のメンバーの和集合** です。

### Workspace のロール

| ロール | できること |
| --- | --- |
| owner | すべて。admin の任命・変更は owner だけ |
| admin | メンバーの招待、member / guest のロール変更と利用停止、Team の作成、Workspace 既定の設定 |
| member | 業務データの作成・更新。管理系の設定は閲覧のみ |
| guest | 閲覧中心。業務データの編集、agent 用 token の発行、agent 設定の変更はできない。自動化の rule・template・定期 Work・実行履歴は見られない |

### Project のロール

Project の task 画面の **権限** タブ（「権限管理」）で、Project ごとに設定します。

| ロール | できること |
| --- | --- |
| manager | 設定変更、メンバー管理、タスク更新 |
| member | タスク作成、状態更新、閲覧 |
| viewer | プロジェクトとタスクの閲覧 |

Project のメンバー権限を変えられるのは、その Project の manager だけです。追加できるのは
Workspace の有効なメンバーだけなので、先に Workspace へ招待しておきます。

Project の権限はその Team の Project にだけ効きます。別の Team に同じ ID の Project があっても、
そちらの Work Item は見えません。複数の Team が同じ Project ID を使っている場合、Team を持たない
旧形式の Project メンバー登録ではどの Team の Project か決められないため、その Project の権限は
どの Team でも効きません。Enterprise では Directory group mapping で Team・Project 単位のロールを
割り当てると、その Team の Project にだけ効きます。

**Team の管理者** は、Workspace の owner / admin、またはその Team のいずれかの Project の manager です
（Enterprise の `teams.manage` 権限を持つ人も含みます）。Team 固有の Work Item 設定と
エージェント設定は Team の管理者が変更します。

Enterprise の組み込みロール（Workspaceオーナー / Workspace管理者 / Workspaceメンバー / ゲスト /
全Project閲覧 / 監査担当 / Team管理者 / Teamメンバー / Project管理者 / Projectメンバー /
Project閲覧者）と Custom role は [ID・セキュリティ](#idセキュリティ) で扱います。
Enterprise ロールは Directory group mapping のほか、メンバー個人にも直接割り当てられます
（[メンバーへのロール割り当て](#メンバーへのロール割り当て)）。

## メンバーを招待する・外す

**設定** → **Workspace 管理**（`/settings/workspace`）→ **アクセス台帳** で行います（owner / admin のみ。それ以外の人には読み取り専用で表示されます）。

1. **メンバーを招待** に「メールアドレス」「表示名（任意）」とロールを入れ、**招待を作成** を押す。
   admin が選べるのは member と guest、owner はすべてのロールを選べます。
   招待された人には件名「Mukuroji への招待」のメールで、ユーザー名・仮パスワード・サインイン用の URL が届きます。
   仮パスワードは 7 日で切れるので、切れたら **再送** してください。
2. 招待は既定で 7 日後に期限切れになります。状態は「準備中 / 受諾待ち / 配信失敗 / 期限切れ /
   取消済み / 受諾済み」で表示され、**再送**・**取消**・**再招待** ができます。
3. ロールの変更は **ロールを変更**、外すときは **利用停止** です。削除ではないので **再有効化** で戻せます。

### まとめて招待する

**複数のメンバーを招待** に、メールアドレスを1行に1件ずつ貼り付けるか、CSV ファイル（1 MB まで）を選びます。

- CSV は「メールアドレス,名前,ロール」の順に書くか、`email`・`name`・`role`（または「メールアドレス」「名前」「ロール」）の見出し行を付けます。
  名前とロールは省略でき、ロールのない行には **ロール（列がない行）** で選んだロールが付きます。ロールは owner / admin / member / guest で書きます。
- 1回に送れるのは 200 件までです。それより多い行は今回は送らず、送ったあと（確認した行がどれも送れないときはすぐに） **まだ招待していない行だけ入力し直す** で入力欄に残せます。残した行は 200 件を超えた行が先に並ぶので、次の確認でその行から調べます。
- **内容を確認** を押すと、まだ何も送らずに行ごとの確認結果が出ます。メールアドレスの形式の誤り、名前が128文字を超える、
  付与できないロール、同じ入力の中での重複、すでにメンバー、すでに招待中の行は送られません。
  期限切れ・取消済みなど以前の招待がある人は新しく招待できないので、招待一覧の **再招待** を使います。
- **N 件を招待** で送れる行だけを送り、行ごとに「招待しました」か、招待できなかった理由（ドメイン制限など）が出ます。
  各行は1回だけ送ります。**まだ招待していない行だけ入力し直す** で送れなかった行（と 200 件を超えた行）を入力欄に戻し、もう一度 **内容を確認** すると、
  最新の招待一覧と照らして次にすること（直して送る、配信に失敗した招待は招待一覧の **再送** を使う、など）が出ます。

招待した人を最初から Project に入れることはまだできません。受諾して Workspace の有効なメンバーになってから、Project の権限タブで追加してください。

### メンバーを探す・書き出す

**Workspace メンバー** の上の検索欄に名前かメールアドレスの一部を入れると、一覧が絞り込まれます。全角・半角、大文字・小文字、空白の有無は区別しません
（「佐藤花子」で「佐藤 花子」が見つかります）。利用状態とロールでも絞り込めます。
**CSV に書き出す** は、いま表示しているメンバーのメールアドレス・表示名・ロール・利用状態・参加日時・利用停止日時を書き出します。
書き出した CSV はそのまま一括招待の入力に使える形式です。

利用停止できないケース:

- 自分自身
- 最後の有効な owner
- まだ Project の manager であるか、計画データ（Goal など）の所有者になっている人。先に引き継いでください

## Team と Project を作る

- サイドバーの **チームを追加** から「新規登録」を開き、**チーム** を選んで「チーム名」と「色」を入れ、
  **チームを登録** を押します（owner / admin のみ）。
- 同じ画面の **プロジェクト** で「登録先チーム」を選ぶと Project を作れます。Project の進め方は
  [PM ガイド](pm.md) を参照してください。
- アーカイブは「{名前} をアーカイブ」から行います。確認画面には、未完了の Work Item、進行中の Agent Run、
  この Team に配信している Webhook の件数が出ます（件数が多いときは「◯件以上」）。これらは警告で、
  そのままアーカイブできます。Planning の計画・Work Item のリンク・依存関係（Project は Project の Work Item にかかるもの）が残っている間は
  アーカイブできないので、確認画面に出る件数を見て先に移動・アーカイブ・解除してください。
- チームとプロジェクトの名前は日本語名・英語名とも 500 文字までで、改行などの制御文字は使えません。
- **設定** → **Workspace 管理** → **チームとプロジェクトの管理**（owner / admin のみ）で、次の操作ができます。
  - **名前を変更**: 日本語名と英語名（Project は色も）を変えます。英語名を空にすると日本語名を使います。
    ID と URL は変わらないので、ブックマーク・Work Item・リンクはそのまま使えます。
  - **↑ / ↓**: チームの並び順と、チーム内のプロジェクトの並び順を変えます。サイドバーと一覧に反映されます。
    あとから作ったチームやプロジェクトは末尾に並びます。
  - **アーカイブ済み** の **復元**: アーカイブしたチームやプロジェクトを元に戻します。アーカイブ中も
    Work Item とプロジェクトのロールは残っているので、復元すると元どおり使えます。
    チームごとアーカイブしたプロジェクトは、チームを復元すると一緒に戻ります。
    ただし、アーカイブ時に止まった週次進捗の更新スケジュールと、Webhook の Team / Project 単位の許可は
    自動では戻らないので、必要なら設定し直してください。
    アーカイブ直後は Webhook の許可の後始末が終わるまで復元できないことがあります。数分おいてから復元してください。
- **プロジェクトを別のチームへ移す** 機能はありません。Work Item はチームごとの番号（`KEY-12` など）で
  工数・文書・Agent Run・依存関係に結び付いているため、チームを変えると履歴が保てないからです。
  移したいときは、移動先のチームに新しいプロジェクトを作り、元のプロジェクトの Work Item を CSV / JSON で
  export して新しいプロジェクトに import（[API と外部連携](#api-と外部連携) の **Import / Export**）してから、元のプロジェクトをアーカイブしてください。
  元のプロジェクトに Planning の計画や、Work Item のリンク・依存関係が残っているとアーカイブできません。
  アーカイブの確認画面に出る件数を見て、新しいプロジェクトで張り直してから元のほうを解除してください。
  コメントと変更履歴は移らないので、元のプロジェクトはアーカイブのまま残しておけば参照できます。
- **設定** → **チーム** の **チームの設定**（owner / admin のみ。Enterprise のロールでは Workspace 全体の `teams.manage` と `members.read` が必要）で、チームを選んで次の操作ができます。
  - **説明** と **リーダー**: 説明は 2000 文字まで（改行可）、リーダーは有効な Workspace メンバーから選びます。
    リーダーがあとで Workspace から外れても設定は残るので、別の人を選び直してください。
    画面を開いたあとに別の管理者が説明やリーダーを保存していた場合は、上書きせずに止まります。
    編集中に別の管理者の保存が届いたときは、入力中の内容を残したままお知らせが出ます。
    入力中の内容を控えてから **編集を破棄して最新の内容を表示** で最新の内容に切り替え、入力し直して保存してください。
  - **メンバー**: チームのいずれかのプロジェクトに参加している人と、プロジェクトごとのロールを一覧で確認できます。
  - **すべてのプロジェクトに追加**: メンバーとロールを選ぶと、チームの有効なプロジェクト全部に追加します。
    すでに参加しているプロジェクトのロールは変えません。途中で失敗したときは、同じ操作をやり直すと残りだけ追加されます。
    Enterprise のロールでは、チームの有効なプロジェクトすべてで `projects.manage` も必要です。1つでも足りないと、どのプロジェクトにも追加されません。
    アーカイブ済みのプロジェクトと、あとから作ったプロジェクトには追加されません。
    古いデータで別のチームと同じ ID のプロジェクトがあるチームでは、まとめて追加できません。各プロジェクトのメンバー画面から追加してください。
- `/teams/:teamId/members`（サイドバーの **メンバー**）は Team の顔ぶれと負荷を確認する画面で、
  ここからメンバーの追加・削除はできません（チームの設定から追加できます）。
- 同じ画面の **Team の通知リマインド** で、Team のメンバーに届く期限前通知・期限超過の再通知・
  Project manager への escalation・未更新の督促・工数の督促の日数を決めます。変更できるのは Team manager で、
  ほかのメンバーは閲覧だけです。空欄の項目は既定値を使います。メンバーは escalation 以外を自分の通知設定で
  上書きできます。

## Work Item の設定（ワークフローとフィールド）

**設定** → **Team**（`/settings/team`）→ **ワークフローとフィールド** で、業務の種類・状態の流れ・入力項目を決めます。
詳しい契約は [`docs/work-item-configuration.md`](../work-item-configuration.md) にあります。

- **設定範囲**: 「Workspace 既定」（owner / admin）と「{Team} 固有」（Team の管理者）。
  Team の設定があればそれを、なければ Workspace 既定を、それもなければ組み込みの既定値を使います。
  項目ごとの部分的な継承はありません。継承中の範囲で保存すると、その範囲の上書き設定が作られます。
- **状態の流れ**: **ワークフローを追加**・**状態を追加** で状態を作り、「作成時の初期状態」と
  「遷移マトリクス」で使える遷移を決めます。状態は バックログ / 未着手 / 進行中 / 完了 / キャンセル
  のいずれかの区分に属します。組み込みの状態は todo / in-progress / review / done です。
- **入力スキーマ**: **フィールドを追加** で独自項目を作ります。種類はテキスト / 数値 / 真偽値 / 日付 /
  単一選択 / 複数選択 / 担当者 / 金額 / 期間 / 数式 です。必須にする、適用する Project を絞る、
  既定値や入力チェックを付けることができます。
- **業務の種類**: **種類を追加** で Work Item Type を作り、既定のワークフロー・項目・子にできる種類を決めます。
- **進捗率の算出方法**（ステータス区分 / 見積と残工数 / 手入力）、**子が未完了の親を完了にするとき**
  （警告する / 拒否する）、**ジョブロール**（最大100件）もここで設定します。
- 最後に **設定を保存** を押します。他の人が先に保存していた場合は保存できないので、再読み込みしてやり直します。

使用中のワークフローや状態は削除できません。優先度は 高 / 中 / 低 の3段階で固定です。ラベル（タグ）機能はありません。

## Work Item key の prefix

**設定** → **Team**（`/settings/team`）→ **Work Item key の prefix** で、Team の新しい Work Item の key
（例: `PT-12` の `PT`）を変えられます。変更できるのは Team の管理者です。

- Team の Project に Project code があれば、候補のボタンから選べます（`-` や `_` を除き、先頭の 10 文字）。
  英字で始まる 2〜10 文字の英数字なら自由に入力もできます。
- 別の Team が使っている prefix は選べません。
- 変更後も、これまでの key（例: `PT-12`）でその Work Item を開けます。番号は続きから振られます
  （`PT-12` の次に `CORE` に変えると `CORE-13`）。
- まだ Work Item がない Team では、最初の Work Item より前に prefix を決められます。

## オートメーション

**設定** → **Workspace 管理** → **オートメーション**（変更は owner / admin のみ）。詳細は [`docs/automation.md`](../automation.md)。

| タブ | 内容 |
| --- | --- |
| ルール | 「トリガー」「条件（任意）」「アクション」を組み合わせたルール。作成直後は停止状態なので **有効化** する |
| Webhook | 外部からルールや Triage を起動する受信 endpoint。署名用 secret は作成時に一度だけ表示される |
| テンプレート | Work Item / Project / Workflow のひな形。**複製**・**適用** |
| 繰り返し作業 | 毎日 / 毎週 / 毎月 の定期作成。止まっていた間の分は スキップ / 最新の1件だけ / すべて から選ぶ |
| 実行履歴 | 各ルールの実行結果。失敗したものは **再試行** できる |

トリガーは ステータス変更、担当者変更、期限変更・到来、ベースラインより遅れ、カスタムフィールド変更、Work Item Type 変更、
コメント、親子・blocker の変更、フォーム送信、Webhook 受信、スケジュール。「ベースラインより遅れ」は、予定終了日が Project の今のベースラインより
指定した日数（空欄なら1日）以上遅れた変更で1回だけ動きます。
「親子・blocker の変更」は「対象の変更」で blocker の解除などを 1 つ選ぶか、すべての変更で動かします。
変更は両方の Work Item に記録されるので、たとえば「blocker の解除」は block されていた側の Work Item でだけ動きます。アクションは 担当者を割り当て、状態の移動、
フィールドを更新、Work Item を作成、コメントを追加、通知を送信、承認を依頼、Webhook を送信 です。
暴走を防ぐため「最大試行回数」と「1分あたりの最大実行数」を必ず確認してください。

Project テンプレートには WBS（作業の木）を書けます。「WBS」欄に 1 行 1 作業で
`タイトル | 開始（稼働日） | 日数（稼働日）` と書き、子の作業は行頭に半角スペース 2 つずつ足して字下げします。
例: `要件定義 | 0 | 5` の次の行に `  ヒアリング | 0 | 2`。適用するときに Team と **開始日** を選ぶと、
Project と一緒に WBS の Work Item（担当者は適用した人）が開始日から稼働日（Workspace の稼働カレンダー）で日付を割り当てて作られます。

「Phase / Milestone」欄には Planning の Phase を `タイトル | 開始（稼働日） | 日数（稼働日）`、Milestone を先頭に ◆ を付けて `◆ タイトル | 日付（稼働日）` で書きます。
Phase の次の行に半角スペース 2 つ字下げした Milestone は、その Phase の下に入ります。
タイトルに `|` を含めてもかまいません。Phase のタイトルは ◆ で始められません。
「WBS 内の依存」欄には `1 -> 2` のように WBS 番号（WBS 欄の上から 1、1.1、2 …）で先行と後続を書き、
続けて種類（FS・SS・FF・SF、書かなければ FS）と暦日のずれ（`+2` など）を書けます。

Phase / Milestone を持つテンプレートを適用するときは、Phase を置く Planning の親（roadmap・initiative・goal）も選びます。
適用の前に **プレビュー** を押すと、作る Work Item・Phase・Milestone の件数と日付、依存の数、問題（必須項目の不足、依存を満たさない日付、親の選び間違いなど）が表示されます。
プレビューに問題がなくなってから **適用** を押せます。開始日・Team・親を変えたとき、またはテンプレートが更新されたときは、もう一度プレビューしてください。プレビューの後にほかの管理者がテンプレートや稼働カレンダー（休日など）を変えた場合も、適用すると「もう一度プレビューしてください」と表示され、何も作られません。
選べる親がないと表示された場合は、別の Team を選ぶか、Planning で Workspace かその Team の roadmap・initiative・goal を作ってください。

## リクエスト受付

`/requests`（サイドバーの **リクエスト**）の **フォームとルーティング** タブ（owner / admin のみ）で、
社内外からの依頼を受けるフォームを作ります。詳細は [`docs/request-intake.md`](../request-intake.md)。

1. 「フォーム設定」で「管理用フォーム名」、範囲（Workspace / Team）、「Access mode」
   （Public / ログイン必須 / Internal）、「Link 有効期限」を決める。
2. 項目、表示条件、同意文、添付ファイルの扱いを設定する。
3. 「既定 routing と Work Item mapping」と「回答別 routing rules」で、どの Team の Triage に入れるかを決める。
4. **Draft を保存** で下書き、**公開 version を作成** で公開し、「公開 link」を **Link をコピー** で共有する。

送信された依頼は Team の **Triage** に入ります。依頼者には受付番号と返信スレッドが表示されます。

## API と外部連携

**設定** → **Workspace 管理** → **API と外部連携** のタブで扱います（owner / admin）。詳細は [`docs/public-api.md`](../public-api.md)。

- **認証情報**: **API key を作成**、**OAuth app を登録**（client_credentials のみ）。secret は一度だけ表示されます。
  必要最小限の scope（work-items / webhooks / integrations / imports の read / write など）を選び、
  不要になったら **失効** します。ここで「メンバーによる agent 用キーの発行」を許可・停止できます。
  OAuth app の access token は、app ごとに 1 つの rate limit を共有します。token を発行し直しても残数は戻りません。
  timeout 後に新しい token で再送するときも、同じ `Idempotency-Key` を使えば二重に作成されません。
  「最終利用」は 1 分ごとにまとめて記録するため、最大 1 分遅れて表示されます。
- **Webhook**: 外部への通知。**Webhook を追加** で送信先と「配信を許可する Team」を決めます。配信 log から再送できます。
  Work Item の作成・更新・削除に加えて、親の変更、子の追加・削除、blocker の追加・解除、関連の追加・削除、
  並び順の変更も選べます。これらは相手の Work Item を含まず、変更された側の Work Item だけを送ります。
  Work Item を削除して消えた関係は、残った相手の Work Item の解除・削除として送ります。
- **Connector**: GitHub、Slack、Gmail、Google Calendar、Google Drive との連携。
  一覧には、運用者がこの環境で設定した provider だけが出ます（設定は [`cdk/README.md`](../../cdk/README.md) の
  connector secret）。設定がなければ「利用できる connector はありません」と表示されます。
  設定から外した provider に接続済みの account は一覧に残り、切断はできますが新しい接続はできません。
  接続は、**接続** を押した本人が provider の画面で許可したあと、同じアカウントでログインしたまま
  Mukuroji に戻ると完了します。許可の URL を別の人に送ったり、ログインが切れた状態で戻ったり、
  期限（約10分）が切れたりした場合は完了できないので、この画面からもう一度接続してください。
  **再接続** も同じで、押した本人が完了します。
- **Import / Export**: Work Item の CSV / JSON / Excel / MS Project XML の export と、検証（dry-run）してから確定する import。
  export には親子・WBS 番号・依存・relation・Contributor・受け入れ条件が入り、そのまま import し直せます。
  ただし MS Project XML には依存の日付制約（「この日より後に終える」など）を書けないため、制約のある依存を
  MS Project XML で import し直すと制約はなくなります。制約を残すときは CSV・JSON・Excel を使ってください。
  親子でも依存でもない relation と受け入れ条件は、MS Project XML でも Task のテキスト項目に残り、import し直せます。
  import の mapping では、WBS 番号・アウトラインの深さ・親のキーから親子を、先行タスク（`1.2FS+2d` など）から依存を、
  Contributor と受け入れ条件もあわせて取り込めます。Excel と MS Project XML の file も選べ、file を選ぶと mapping を提案します。書き方と dry-run で見つかる error は
  [Public API の説明](../public-api.md#階層依存contributor受け入れ条件の-import) にあります。

## AI assistance の接続先と API キー

**設定** → **個人** の **AI assistance** で、Workspace policy（使える workflow と model）を owner / admin が決めます。
model は、運用者が設定した Amazon Bedrock の model に加えて、Claude API（`claude-sonnet-5-5`、`claude-opus-5-5`、
`claude-haiku-5-5`）と OpenAI（`gpt-6.2-sol`）から選べます。この環境で使える model は「許可する model ID」の下に表示されます。

- Claude API と OpenAI を使うには、同じ画面の **外部 AI の API キー** に、提供元の管理画面で発行したキーを
  provider ごとに1つ **登録** します。キーは Workspace の全員で共有し、token 料金はその提供元のアカウントにかかります。
- キーは暗号化して保存し、登録後は末尾4文字だけが表示されます。キーをもう一度見ることはできません。
  変えるときは **差し替え**、使わなくなったら **削除** します。登録・差し替え・削除は監査ログに残ります（キーの中身は残りません）。
- キーが登録されていない provider の model で生成すると、「API キーが登録されていません」と表示されます。
- 外部の model を選ぶと、AI に送る内容（メンバー名などは仮名に置き換えた後のもの）は AWS の外の提供元へ送られます。
  社外に出したくない Workspace では、許可する model を Bedrock の model だけにしてください。
- この欄が出ないときは、運用者が外部 provider を無効にしています（[`cdk/README.md`](../../cdk/README.md) の `AiExternalProviders`）。

## エージェント設定（Software factory）

coding agent に任せる作業の範囲を Team ごとに決めます。**設定** → **Team** → **エージェント設定**
（変更は Team の管理者のみ）。仕組みは [`docs/software-factory.md`](../software-factory.md)。

この欄は Software factory を有効にして deploy した環境（CDK context `mukuroji:softwareFactory=true`）にだけ
表示されます。既定の deploy では Factory board、Work Item の「エージェントへ引き継ぐ」と Run 履歴も
表示されず、API は Agent Run 系の操作を `503 SoftwareFactoryNotDeployed` で断ります
（[`cdk/README.md`](../../cdk/README.md#optional-modules)）。**agent を接続** と自分用 token の発行は off でも使え、
設定例は Workspace を読むだけの Workspace profile になります。

- 「リース時間（分）」: agent が作業を確保しておける時間（5〜240分、既定30分）。
  期限切れ後に同じ担当者の別インスタンスが引き継ぐことを許可するかも選べます。
- 「着手可能なステータス」: agent に提示してよい状態（バックログ / 未着手の区分から選ぶ）。
- 「受け入れ条件がある Work Item だけを提示する」: 完了条件のないタスクを agent に渡さないための設定。
- 「再開できるステータス」: 作業中（started）の区分のうち、止まったタスクを担当者の agent が自分で再開してよい状態。
  agent が一時停止した、またはレビューで差し戻されて作業中に戻ったタスクで、実行中の Run がないものが対象です。
  選んだ状態のタスクは agent が次のタスクを探すときに再開候補として提示され、それ以外の状態からは再開できません。
  何も選ばない場合は自動では提示せず、ユーザーが agent に続きを指示したときだけ、作業中のどの状態からでも再開します。
  レビュー中のように人の作業を待つ状態は選ばないでください。
- 失敗・停滞した Run を Triage に自動で起票するかどうか。
- 「エージェント向けブリーフ」: Team と Project ごとに agent へ渡す前提知識（各 16 KiB まで）。

保存は **エージェント設定を保存**。agent の稼働状況は Team の **Factory board** で確認します
（[coding agent 利用者ガイド](coding-agent.md#factory-board)）。

## ID・セキュリティ

`/settings/security`（**設定** → **Workspace 管理** の「ID・セキュリティ管理」から開く）。Enterprise のセキュリティ権限が
ない人には読み取り専用で表示されます。詳細は [`docs/enterprise-identity.md`](../enterprise-identity.md)。

| タブ | 主な設定 |
| --- | --- |
| 概要 | SSO を強制する前の準備状況（IdP の接続テスト、ドメイン確認、緊急管理者） |
| ID | SAML / OIDC の「ID プロバイダー」（**保存して接続テスト**）、「管理対象ドメイン」（DNS TXT で所有権を確認）、「SSO 強制」 |
| プロビジョニング | 「SCIM 接続」の token 発行・ローテーション、「Directory reconciliation」（**Dry-runを実行** → **この差分を適用**）、実行ログ |
| マッピング・ロール | 「Directory group mapping」（Workspace / Team / Project 単位でロールを割り当て）、「メンバーへのロール割り当て」、「ロールと権限」（Custom role の作成） |
| セッション | 「MFAを必須にする」、セッション有効期間、アイドルタイムアウト、再認証間隔、「IP allowlist」、Guest・外部協力者の許可 |
| 特権アクセス | 「Service account」、「緊急管理者」の事前登録と復旧経路のテスト |

SSO を強制する前に、MFA を設定した緊急管理者を登録し、30日以内に **現在の復旧経路をテスト** で
確認しておく必要があります。IdP の障害などでログインできなくなったら、緊急管理者が
`/security/recovery`（「安全に管理アクセスを復旧する」）から理由を書いて 5〜30分の復旧アクセスを開始します。

IP allowlist は CIDR を1行に1つ書きます。空にすると制限なしです。自分の接続元を含め忘れると
締め出されるので、保存前に確認してください。

ログインまわりには、接続元とメールアドレスの組ごとに試行回数の上限があります。上限に達すると、
時間を置くまで同じ操作ができません。

| 操作 | 上限 |
| --- | --- |
| MFA コードの確認、初回パスワードの設定、認証アプリ登録の確認 | 5分ごとに10回 |
| パスワード再設定メールの送信 | 15分ごとに5回 |
| パスワード再設定コードの確認 | 15分ごとに10回 |

回数は区切られた時間枠ごとに数え、成功しても枠が終わるまで減りません。たとえば MFA コードを
何度か間違えてからログインし、すぐに再ログインして上限に達した場合は、最大5分待ってください。
回数はメールアドレスごとに分けて数えるので、他の人の失敗で自分が止められることはありません。

### メンバーへのロール割り当て

「マッピング・ロール」タブの「メンバーへのロール割り当て」で、メンバー・適用範囲（Workspace / Team /
Project）・ロールを選んで **割り当てを追加** します。SCIM や IdP の group がなくても使えます。
複数の Team に属する Project を選んだときは、どの Team の Project として割り当てるかも選びます。
割り当てと解除は監査ログに `role-assignment.created` / `role-assignment.deleted` として残ります。
監査ログではメンバーをメールアドレスではなく、メンバーごとの仮名の ID で示します。

- **全Project閲覧**: 全 Team・全 Project を、Project のメンバーでなくても閲覧できます。編集はできません。
  PMO や経営層向けです。
- **監査担当**: 監査ログ（`/api/audit/events`）を閲覧できます。export はできません。

割り当てを1件でも持つメンバーは、Workspace のロールと Project メンバーとしての権限ではなく、
割り当てたロールの和集合だけで権限が決まります。たとえば Project の manager に「全Project閲覧」を
付けると、その Project も閲覧だけになるので、編集が要る Project には Project管理者などを同じ画面で
追加で割り当ててください。割り当てをすべて解除すると、元の Workspace のロールに戻ります。

- owner と自分自身には割り当てられません。admin への割り当ての追加・解除と、管理系の権限
  （メンバー管理・セキュリティ管理・監査ログの export など）を含むロールの付与・解除は owner だけができます。
  メンバーに割り当て済みの Custom role に管理系の権限を足すことも、owner だけができます。
- 割り当てを持つメンバーを owner / admin に変更するときは、先に割り当てをすべて解除してください。
- メンバーの最後の割り当てを解除すると元のロールに戻るため、owner 以外は、そのメンバーが戻って得る
  権限を自分も持っている場合だけ最後の1件を解除できます。無効化したメンバーも、再有効化すると元の
  ロールに戻るので同じです。
- ゲストには、ゲストに割り当て可能なロール（ゲスト、Project閲覧者、ゲスト可の Custom role）だけを
  割り当てられます。割り当て後にゲストへ変更した場合、それ以外のロールは効かなくなります。
- 割り当てを変更できるのは、Enterprise の `security.manage` または `members.manage` を持つ人です。
  自分が持っていない権限を含むロールは割り当てられません。
- 割り当ての追加・解除や owner / admin への変更の途中で、別の人がそのメンバーのロールや割り当てを
  変えると、操作は取り消されて「変更されました。再読み込みしてください」という旨のエラーになります。
  画面を再読み込みして、今の状態を確かめてからやり直してください。

## テナント管理

**設定** → **Workspace 管理** → **テナント管理**（owner / admin のみ）。詳細は [`docs/tenant-administration.md`](../tenant-administration.md)。

- 「テナント profile」: owner、region、locale、招待時にロールを省略したときの「既定 member role」。
  「会計年度の開始月」と「週の開始曜日」もここで決めます。週の開始曜日は工数のタイムシート・承認・週報の週と、工数レポートの週ごとの集計、要員計画の週単位の表示、レポートの期間（今週・先週）、カレンダーとガントの週、新しい週単位 Cycle の開始日、レポートの毎週の配信の既定の曜日に使われます。会計年度の開始月はレポートの期間（今四半期・今年度など）、ガントの四半期の列、工数の予算を年度で指定するときに使われます。決めていなければ 1 月始まり・月曜始まりです。
  「稼働曜日」、「日本の祝日を休日にする」、「会社の休日」（日付を選んで **休日を追加**、最大512日）も Workspace 全体で決めます。
  日本の祝日（振替休日を含む）は内閣府が公表する一覧を毎月初めに自動で取り込むので、会社の休日に足す必要はありません。
  取り込めないときは前回取り込んだ一覧、それも無ければアプリに同梱した一覧を使います（出典: 内閣府「国民の祝日」について）。
  新しく作る Work Item は、task 画面・Team の Issue 画面・Public API・MCP・Project template の適用・依頼フォーム・import の
  どれから作っても、この稼働曜日と休日で稼働日数を数えます。Project・Team の Issue・My Tasks の Gantt の日単位の列と
  Calendar の日付では、稼働日でない日を網掛けし、Calendar には「休み」と出します。
  保存しただけでは、すでにある Work Item の日程は変わりません。決めていなければ月〜金が稼働日で、日本の祝日が休日です。
  保存後に下の「Work Item の日程を Workspace カレンダーに合わせる」で **影響を確認** を押すと、日程が変わる Work Item の数と例が出ます。
  「期間（稼働日数）を保つ」か「終了日を保つ」を選んで
  **適用** すると、Team・Project のカレンダーに従う Work Item の日程が揃います。自分で稼働日を決めた Work Item は変わりません。
  「タイムゾーン」（`Asia/Tokyo` のような IANA 名）では、新しく作る Work Item の期限・期限切れの判定、
  週報のリマインダーの時刻、要員計画で「Workspace のカレンダーを使う」メンバーの稼働日はこのタイムゾーンで数えます。
  決めていなければ日本時間です。すでにある Work Item は作ったときのタイムゾーンのままです。
  Team メンバー画面の要員計画の「稼働プロファイル」は、新しく作ると「Workspace のカレンダーを使う」になり、
  稼働曜日・会社の休日・祝日・タイムゾーンをここから受け継ぎます。メンバーごとには 1 日の勤務時間、
  勤務しない曜日（Workspace が稼働する曜日のうち）、「個人の休み」と休暇だけを持ちます。
  チェックを外すと、そのメンバーだけ独自のタイムゾーンと休日を使います（以前に保存したプロファイルはこちらのままです）。
  「週報のリマインダー」では、週報を出していない本人に知らせる曜日・時刻と、まだ出していないときに
  その人が参加している Project の manager に知らせる曜日・時刻を決めます（Workspace のタイムゾーン、1 時間単位。それぞれ止められます）。通知は 1 時間ごとの確認で送るため、指定した時刻の 1 時間のうちに届きます（UTC との差が 1 時間単位でないタイムゾーンでは、その時の途中に届きます）。夏時間の始まりで指定した時刻が飛ばされる日は、その直後の時刻に送ります。
  決めていなければ本人へ金曜 17 時、manager へ月曜 10 時です。2 つを同じ曜日・時刻にはできません。
  「工数の作業区分」では、メンバーが工数を記録するときに選ぶ区分（設計・実装・会議など）を決めます。
  既定の 7 区分は名前を変えられ、名前を空にすると標準の名前に戻ります。**区分を追加** で Workspace 独自の区分も足せます（最大 50 区分、名前は 60 文字まで）。
  上下のボタンで並び順を変えられます。使わなくなった区分は削除せず「使う」を外します。外した区分は新しい記録では選べませんが、
  すでに記録した工数と提出済みの週報には名前が残り、その区分のままの工数はそのまま編集できます。少なくとも 1 区分は「使う」にしてください。
  集計の「作業区分」別と CSV には、ここで付けた名前が出ます。
  「通貨」は、工数の原価・単価表・予算で通貨を指定しないときに使う通貨です（JPY・USD・EUR）。決めていなければ JPY です。
  変えても保存済みの金額の通貨は変わりません。
- 「データ governance」: 監査ログの保持日数（30日以上）と legal hold。
- 「Export と閉鎖」: テナント全体の export（成果物は30日で失効）と、テナントの閉鎖
  （`CLOSE` と入力して開始。中断・再開・検証ができます）。
  export には監査ログが含まれるため、開始とダウンロードには監査ログの export 権限（`audit.export`）が要ります。
  組み込みロールでは owner だけが持ち、admin は export できません。ダウンロード URL の発行は監査ログに記録されます。
  export・閉鎖・ダウンロードと操作の中断・再開・検証は、セキュリティポリシーの「重要操作の再認証」の対象です。

運用者が runtime control（メンテナンスの切り替えと停止・再開）を切り替えると、監査ログに
`runtime-control.change-started` と、`runtime-control.change-completed` または `runtime-control.change-failed` が残ります。
切り替えた AWS の実行者（GitHub Actions からの場合は起動した GitHub のユーザーと run）と時刻が分かります。
開始を監査ログに書けないときは、メンテナンスの切り替えと再開は何も変えずに止まります。停止は開始を書けなくても警告を出して続け、
完了・失敗の記録はあらためて書きます。開始・完了・失敗のどの記録も、書けなかったときは警告だけが出て、その記録は残りません。
監査用の stack output が無い stack での停止は、警告を出して記録を書かずに続けます。警告が出たら変更記録に残してください。

## Team・Project の稼働カレンダー

**設定** → **Team**（`/settings/team`）→ **稼働カレンダー（Team・Project）** で、Team や Project ごとに
稼働曜日・日本の祝日・追加の休日を決めます。決めていない項目は Workspace の稼働カレンダー（Project は Team のカレンダー）を引き継ぎます。
追加の休日は引き継いだ休日に足されます（最大128日）。

- 変更できるのは Team 設定を管理できる人です。Project のカレンダーは、その Project の manager も変更できます。
  それ以外の人には読み取り専用で表示されます。
- 変えたら **影響を確認** を押し、日程が変わる Work Item の数と例（最大10件）を確かめてから **保存して適用** します。
  「期間（稼働日数）を保つ」は開始日はそのままで終了日を動かし、「終了日を保つ」は開始日と終了日はそのままで稼働日数を数え直します
  （数え直して 0 日になる Work Item は期間を保ちます）。Team で選んだ方はその Team の次回の既定になり、
  Project の画面でも Team で選んだ方が最初に選ばれます。
- 日程が変わるのは、Team・Project のカレンダーに従う Work Item だけです。タスク詳細で稼働日を個別に決めた Work Item は変わりません。
- 新しく作る Work Item は、作成先の Project（無ければ Team）のカレンダーで稼働日数を数えます。
- ほかの人が先に保存していると「変更されました」という旨のエラーになるので、読み込み直してやり直してください。
  一度に日程を変えられる Work Item は480件までです。

## 監査ログを見る

**設定** → **Workspace 管理** → **監査ログ**。owner / admin と、監査ログの閲覧権限（`audit.read`。組み込みの「監査担当」ロールが持ちます）か
export 権限（`audit.export`）を持つ人にだけ表示されます。ほかの人には画面も記録も表示されません。
export 権限だけを持つカスタムロールの人は検索できず、export だけを使えます。

- 「実行者 ID」「種類」「対象の種類」「対象 ID」「開始日」「終了日」で絞り込み、**検索** を押すと新しい順に 50 件ずつ表示します。
  **さらに読み込む** で続きを読みます。読み込んだ範囲に一致がなくても古い記録が残っていれば **さらに読み込む** が出ます。期間は個人設定のタイムゾーンで日単位に数えます（開始日の 0 時から終了日の終わりまで）。
- 一覧の実行者名を押すとその人の操作だけに、対象の種類を押すとその対象への操作だけに絞り込めます。
  特定のメンバーの先週の操作を調べるときは、その人の操作を 1 件見つけて名前を押し、期間を先週にして検索します。
- 種類は「Work Item の更新」のように日本語（英語表示では英語）で表示し、横に `work-item.updated` のような元の名前を添えます。
  種類の欄では候補から選ぶか元の名前を入力します（カンマ区切りで 20 件まで）。
- 各行の **変更前後を見る** で、項目ごとの変更前と変更後の値、まとめ先、経路（API、システム処理、移行など）、相関 ID を確認できます。
  機密の値は「機密のため非表示」と表示されます。
- 監査ログは検索するたびに、検索したこと自体（`audit.viewed`）が記録されます。そのため画面を開いただけでは読み込まず、**検索** を押したときだけ読み込みます。

export 権限（`audit.export`。組み込みロールでは owner だけ）があれば、同じ画面の「export」で **この条件で export を依頼** を押すと、
上の絞り込みに合う記録を NDJSON ファイルに書き出します。条件を何も入れなければ保持しているすべての記録を書き出します。
ただし、依頼から 24 時間後（秒未満は切り上げ）までに保持期限を迎える記録（その時刻ちょうどのものを含む）は書き出しに含まれません。そうした記録が必要なときは API の同期 export（`GET /api/audit/events/export`）を使います。
書き出しが終わると「完了」になり、**ダウンロードリンクを発行** でファイルごとのリンクが出ます。リンクは 5 分で無効になるので、
切れたらもう一度発行します。依頼（`audit.export-requested`）とリンクの発行（`audit.export-downloaded`）も監査ログに残ります。
export の依頼とリンクの発行は、セキュリティポリシーの「重要操作の再認証」の対象です。

API（`/api/audit/events`、`/api/audit/exports`）からも取得できます。仕様は [`docs/event-audit.md`](../event-audit.md) を参照してください。

## メンテナンスに切り替える

移行作業や障害対応で変更だけを止めたいときは、運用者が `bun run runtime-control:read-only` で
読み取り専用のメンテナンスに切り替えます。閲覧とサインインは続けられ、変更は理由付きで断られます。
すべて止める場合は `bun run runtime-control:disable`、戻すときは `bun run runtime-control:enable` です。
どの場合もメンバーの画面には「メンテナンス中」のバナーが出ます。手順は
[cdk/README.md](../../cdk/README.md#application-処理を有効にするruntime-control) を参照してください。

## まだ提供していない機能

  （[`docs/external-chat-sync.md`](../external-chat-sync.md)）。Slack は通知の送信先と Connector としては使えます。
- 社外の顧客向けポータルはありません。`/customers` は社内向けの顧客台帳です。
