# 管理者ガイド

Workspace の owner・admin、Team の管理者向けに、メンバーと権限、業務の設定、自動化、
coding agent の受け入れ、Enterprise のセキュリティ設定をまとめます。管理系の画面は
サイドバーの **設定**（`/settings`）と **ID・セキュリティ**（`/settings/security`）に集まっています。

## 権限のしくみ

mukuroji の権限は Workspace と Project の2段階です。Team には独立したメンバー登録がなく、
**Team のメンバー = その Team に属する Project のメンバーの和集合** です。

### Workspace のロール

| ロール | できること |
| --- | --- |
| owner | すべて。admin の任命・変更は owner だけ |
| admin | メンバーの招待、member / guest のロール変更と利用停止、Team の作成、Workspace 既定の設定 |
| member | 業務データの作成・更新。管理系の設定は閲覧のみ |
| guest | 閲覧中心。業務データの編集、agent 用 token の発行、agent 設定の変更はできない。自動化の rule・template・定期 Work・実行履歴は見られない |

### Project のロール

Project の task 画面の **権限** タブ（「権限管理」）で、Project ごとに設定します。

| ロール | できること |
| --- | --- |
| manager | 設定変更、メンバー管理、タスク更新 |
| member | タスク作成、状態更新、閲覧 |
| viewer | プロジェクトとタスクの閲覧 |

Project のメンバー権限を変えられるのは、その Project の manager だけです。追加できるのは
Workspace の有効なメンバーだけなので、先に Workspace へ招待しておきます。

**Team の管理者** は、Workspace の owner / admin、またはその Team のいずれかの Project の manager です
（Enterprise の `teams.manage` 権限を持つ人も含みます）。Team 固有の Work Item 設定と
エージェント設定は Team の管理者が変更します。

Enterprise の組み込みロール（Workspaceオーナー / Workspace管理者 / Workspaceメンバー / ゲスト /
Team管理者 / Teamメンバー / Project管理者 / Projectメンバー / Project閲覧者）と Custom role は
[ID・セキュリティ](#idセキュリティ) で扱います。Team・Project 単位の Enterprise ロールは
Directory group mapping からだけ割り当てられ、個人へ直接は割り当てられません。

## メンバーを招待する・外す

**設定** → **アクセス台帳** で行います（owner / admin のみ。それ以外の人には読み取り専用で表示されます）。

1. **メンバーを招待** に「メールアドレス」「表示名（任意）」とロールを入れ、**招待を作成** を押す。
   admin が選べるのは member と guest、owner はすべてのロールを選べます。
2. 招待は既定で 7 日後に期限切れになります。状態は「準備中 / 受諾待ち / 配信失敗 / 期限切れ /
   取消済み / 受諾済み」で表示され、**再送**・**取消**・**再招待** ができます。
3. ロールの変更は **ロールを変更**、外すときは **利用停止** です。削除ではないので **再有効化** で戻せます。

利用停止できないケース:

- 自分自身
- 最後の有効な owner
- まだ Project の manager であるか、計画データ（Goal など）の所有者になっている人。先に引き継いでください

## Team と Project を作る

- サイドバーの **チームを追加** から「新規登録」を開き、**チーム** を選んで「チーム名」と「色」を入れ、
  **チームを登録** を押します（owner / admin のみ）。
- 同じ画面の **プロジェクト** で「登録先チーム」を選ぶと Project を作れます。Project の進め方は
  [PM ガイド](pm.md) を参照してください。
- アーカイブは「{名前} をアーカイブ」から行います。
- **設定** → **チームとプロジェクトの管理**（owner / admin のみ）で、次の操作ができます。
  - **名前を変更**: 日本語名と英語名（Project は色も）を変えます。英語名を空にすると日本語名を使います。
    ID と URL は変わらないので、ブックマーク・Work Item・リンクはそのまま使えます。
  - **↑ / ↓**: チームの並び順と、チーム内のプロジェクトの並び順を変えます。サイドバーと一覧に反映されます。
    あとから作ったチームやプロジェクトは末尾に並びます。
  - **アーカイブ済み** の **復元**: アーカイブしたチームやプロジェクトを元に戻します。アーカイブ中も
    Work Item とプロジェクトのロールは残っているので、復元すると元どおり使えます。
    チームごとアーカイブしたプロジェクトは、チームを復元すると一緒に戻ります。
    ただし、アーカイブ時に止まった週次進捗の更新スケジュールと、Webhook の Team / Project 単位の許可は
    自動では戻らないので、必要なら設定し直してください。
    アーカイブ直後は Webhook の許可の後始末が終わるまで復元できないことがあります。数分おいてから復元してください。
- `/teams/:teamId/members`（サイドバーの **メンバー**）は Team の顔ぶれと負荷を確認する画面で、
  ここからメンバーの追加・削除はできません。

## Work Item の設定（ワークフローとフィールド）

**設定** → **ワークフローとフィールド** で、業務の種類・状態の流れ・入力項目を決めます。
詳しい契約は [`docs/work-item-configuration.md`](../work-item-configuration.md) にあります。

- **設定範囲**: 「Workspace 既定」（owner / admin）と「{Team} 固有」（Team の管理者）。
  Team の設定があればそれを、なければ Workspace 既定を、それもなければ組み込みの既定値を使います。
  項目ごとの部分的な継承はありません。継承中の範囲で保存すると、その範囲の上書き設定が作られます。
- **状態の流れ**: **ワークフローを追加**・**状態を追加** で状態を作り、「作成時の初期状態」と
  「遷移マトリクス」で使える遷移を決めます。状態は バックログ / 未着手 / 進行中 / 完了 / キャンセル
  のいずれかの区分に属します。組み込みの状態は todo / in-progress / review / done です。
- **入力スキーマ**: **フィールドを追加** で独自項目を作ります。種類はテキスト / 数値 / 真偽値 / 日付 /
  単一選択 / 複数選択 / 担当者 / 金額 / 期間 / 数式 です。必須にする、適用する Project を絞る、
  既定値や入力チェックを付けることができます。
- **業務の種類**: **種類を追加** で Work Item Type を作り、既定のワークフロー・項目・子にできる種類を決めます。
- **進捗率の算出方法**（ステータス区分 / 見積と残工数 / 手入力）、**子が未完了の親を完了にするとき**
  （警告する / 拒否する）、**ジョブロール**（最大100件）もここで設定します。
- 最後に **設定を保存** を押します。他の人が先に保存していた場合は保存できないので、再読み込みしてやり直します。

使用中のワークフローや状態は削除できません。優先度は 高 / 中 / 低 の3段階で固定です。ラベル（タグ）機能はありません。

## オートメーション

**設定** → **オートメーション**（変更は owner / admin のみ）。詳細は [`docs/automation.md`](../automation.md)。

| タブ | 内容 |
| --- | --- |
| ルール | 「トリガー」「条件（任意）」「アクション」を組み合わせたルール。作成直後は停止状態なので **有効化** する |
| Webhook | 外部からルールや Triage を起動する受信 endpoint。署名用 secret は作成時に一度だけ表示される |
| テンプレート | Work Item / Project / Workflow のひな形。**複製**・**適用** |
| 繰り返し作業 | 毎日 / 毎週 / 毎月 の定期作成。止まっていた間の分は スキップ / 最新の1件だけ / すべて から選ぶ |
| 実行履歴 | 各ルールの実行結果。失敗したものは **再試行** できる |

トリガーは ステータス変更、担当者変更、期限変更・到来、カスタムフィールド変更、Work Item Type 変更、
コメント、フォーム送信、Webhook 受信、スケジュール。アクションは 担当者を割り当て、状態の移動、
フィールドを更新、Work Item を作成、コメントを追加、通知を送信、承認を依頼、Webhook を送信 です。
暴走を防ぐため「最大試行回数」と「1分あたりの最大実行数」を必ず確認してください。

Project テンプレートには WBS（作業の木）を書けます。「WBS」欄に 1 行 1 作業で
`タイトル | 開始（稼働日） | 日数（稼働日）` と書き、子の作業は行頭に半角スペース 2 つずつ足して字下げします。
例: `要件定義 | 0 | 5` の次の行に `  ヒアリング | 0 | 2`。適用するときに Team と **開始日** を選ぶと、
Project と一緒に WBS の Work Item（担当者は適用した人）が開始日から稼働日（月〜金）で日付を割り当てて作られます。

## リクエスト受付

`/requests`（サイドバーの **リクエスト**）の **フォームとルーティング** タブ（owner / admin のみ）で、
社内外からの依頼を受けるフォームを作ります。詳細は [`docs/request-intake.md`](../request-intake.md)。

1. 「フォーム設定」で「管理用フォーム名」、範囲（Workspace / Team）、「Access mode」
   （Public / ログイン必須 / Internal）、「Link 有効期限」を決める。
2. 項目、表示条件、同意文、添付ファイルの扱いを設定する。
3. 「既定 routing と Work Item mapping」と「回答別 routing rules」で、どの Team の Triage に入れるかを決める。
4. **Draft を保存** で下書き、**公開 version を作成** で公開し、「公開 link」を **Link をコピー** で共有する。

送信された依頼は Team の **Triage** に入ります。依頼者には受付番号と返信スレッドが表示されます。

## API と外部連携

**設定** → **API と外部連携** のタブで扱います（owner / admin）。詳細は [`docs/public-api.md`](../public-api.md)。

- **認証情報**: **API key を作成**、**OAuth app を登録**（client_credentials のみ）。secret は一度だけ表示されます。
  必要最小限の scope（work-items / webhooks / integrations / imports の read / write など）を選び、
  不要になったら **失効** します。ここで「メンバーによる agent 用キーの発行」を許可・停止できます。
  OAuth app の access token は、app ごとに 1 つの rate limit を共有します。token を発行し直しても残数は戻りません。
  timeout 後に新しい token で再送するときも、同じ `Idempotency-Key` を使えば二重に作成されません。
  「最終利用」は 1 分ごとにまとめて記録するため、最大 1 分遅れて表示されます。
- **Webhook**: 外部への通知。**Webhook を追加** で送信先と「配信を許可する Team」を決めます。配信 log から再送できます。
- **Connector**: GitHub、Slack、Gmail、Google Calendar、Google Drive との連携。
- **Import / Export**: Work Item の CSV / JSON export と、検証（dry-run）してから確定する import。

## エージェント設定（Software factory）

coding agent に任せる作業の範囲を Team ごとに決めます。**設定** → **エージェント設定**
（変更は Team の管理者のみ）。仕組みは [`docs/software-factory.md`](../software-factory.md)。

- 「リース時間（分）」: agent が作業を確保しておける時間（5〜240分、既定30分）。
  期限切れ後に同じ担当者の別インスタンスが引き継ぐことを許可するかも選べます。
- 「着手可能なステータス」: agent に提示してよい状態（バックログ / 未着手の区分から選ぶ）。
- 「受け入れ条件がある Work Item だけを提示する」: 完了条件のないタスクを agent に渡さないための設定。
- 「再開できるステータス」: 作業中（started）の区分のうち、止まったタスクを担当者の agent が自分で再開してよい状態。
  agent が一時停止した、またはレビューで差し戻されて作業中に戻ったタスクで、実行中の Run がないものが対象です。
  選んだ状態のタスクは agent が次のタスクを探すときに再開候補として提示され、それ以外の状態からは再開できません。
  何も選ばない場合は自動では提示せず、ユーザーが agent に続きを指示したときだけ、作業中のどの状態からでも再開します。
  レビュー中のように人の作業を待つ状態は選ばないでください。
- 失敗・停滞した Run を Triage に自動で起票するかどうか。
- 「エージェント向けブリーフ」: Team と Project ごとに agent へ渡す前提知識（各 16 KiB まで）。

保存は **エージェント設定を保存**。agent の稼働状況は Team の **Factory board** で確認します
（[coding agent 利用者ガイド](coding-agent.md#factory-board)）。

## ID・セキュリティ

`/settings/security`（**設定** の「ID・セキュリティ管理」から開く）。Enterprise のセキュリティ権限が
ない人には読み取り専用で表示されます。詳細は [`docs/enterprise-identity.md`](../enterprise-identity.md)。

| タブ | 主な設定 |
| --- | --- |
| 概要 | SSO を強制する前の準備状況（IdP の接続テスト、ドメイン確認、緊急管理者） |
| ID | SAML / OIDC の「ID プロバイダー」（**保存して接続テスト**）、「管理対象ドメイン」（DNS TXT で所有権を確認）、「SSO 強制」 |
| プロビジョニング | 「SCIM 接続」の token 発行・ローテーション、「Directory reconciliation」（**Dry-runを実行** → **この差分を適用**）、実行ログ |
| マッピング・ロール | 「Directory group mapping」（Workspace / Team / Project 単位でロールを割り当て）、「ロールと権限」（Custom role の作成） |
| セッション | 「MFAを必須にする」、セッション有効期間、アイドルタイムアウト、再認証間隔、「IP allowlist」、Guest・外部協力者の許可 |
| 特権アクセス | 「Service account」、「緊急管理者」の事前登録と復旧経路のテスト |

SSO を強制する前に、MFA を設定した緊急管理者を登録し、30日以内に **現在の復旧経路をテスト** で
確認しておく必要があります。IdP の障害などでログインできなくなったら、緊急管理者が
`/security/recovery`（「安全に管理アクセスを復旧する」）から理由を書いて 5〜30分の復旧アクセスを開始します。

IP allowlist は CIDR を1行に1つ書きます。空にすると制限なしです。自分の接続元を含め忘れると
締め出されるので、保存前に確認してください。

ログインまわりには、接続元とメールアドレスの組ごとに試行回数の上限があります。上限に達すると、
時間を置くまで同じ操作ができません。

| 操作 | 上限 |
| --- | --- |
| MFA コードの確認、初回パスワードの設定、認証アプリ登録の確認 | 5分ごとに10回 |
| パスワード再設定メールの送信 | 15分ごとに5回 |
| パスワード再設定コードの確認 | 15分ごとに10回 |

回数は区切られた時間枠ごとに数え、成功しても枠が終わるまで減りません。たとえば MFA コードを
何度か間違えてからログインし、すぐに再ログインして上限に達した場合は、最大5分待ってください。
回数はメールアドレスごとに分けて数えるので、他の人の失敗で自分が止められることはありません。

## テナント管理

**設定** → **テナント管理**（owner / admin のみ）。詳細は [`docs/tenant-administration.md`](../tenant-administration.md)。

- 「テナント profile」: owner、region、locale、招待時にロールを省略したときの「既定 member role」。
  「会計年度の開始月」と「週の開始曜日」もここで決めます。週の開始曜日は工数のタイムシート・承認・週報の週に使われます。決めていなければ 1 月始まり・月曜始まりです。
  「稼働曜日」と「会社の休日」（日付を選んで **休日を追加**、最大512日）も Workspace 全体で決めます。
  task 画面から新しく作る Work Item はこの稼働曜日と休日で稼働日数を数え、Gantt の日単位の列では稼働日でない日を網掛けします。
  すでにある Work Item の日程は変わりません。決めていなければ月〜金が稼働日で、休日はありません。
- 「データ governance」: 監査ログの保持日数（30日以上）と legal hold。
- 「Export と閉鎖」: テナント全体の export（成果物は30日で失効）と、テナントの閉鎖
  （`CLOSE` と入力して開始。中断・再開・検証ができます）。
  export には監査ログが含まれるため、開始とダウンロードには監査ログの export 権限（`audit.export`）が要ります。
  組み込みロールでは owner だけが持ち、admin は export できません。ダウンロード URL の発行は監査ログに記録されます。
  export・閉鎖・ダウンロードと操作の中断・再開・検証は、セキュリティポリシーの「重要操作の再認証」の対象です。

監査ログには現在 Web の画面がありません。API（`/api/audit/events`、`/api/audit/exports`）から取得します。
仕様は [`docs/event-audit.md`](../event-audit.md) を参照してください。

## まだ提供していない機能

- 外部チャット（Slack / Microsoft Teams）とのスレッド同期は契約のみで、画面と接続はまだありません
  （[`docs/external-chat-sync.md`](../external-chat-sync.md)）。Slack は通知の送信先と Connector としては使えます。
- 社外の顧客向けポータルはありません。`/customers` は社内向けの顧客台帳です。
